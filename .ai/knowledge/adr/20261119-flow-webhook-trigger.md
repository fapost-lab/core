# A flow's webhook trigger is served by Laravel on the tenant's host, its secret lives encrypted outside the definition, and a delivery runs once

## Context

Spec `flow-automations` (phase 7) asks for a webhook trigger: an outside system starts a flow over HTTP, checked by a
signature or a shared secret, deduplicated by `(trigger, delivery id)`. Until now the `webhook` trigger type existed only
as a form: its config held `method`, `path` and the secret in plain text, and nothing served a request. Since
`adr-20261119-flow-triggers-in-definition-live-on-publish` a trigger's config is copied into the draft and every
published definition (and into templates and a future export), so a secret there would spread to every version. The
channel webhooks (`app/Domains/Webhook`) run on the base domain through a landlord registry and may not touch Eloquent
or the tenant context. The URL handed to outside systems is the costliest thing to change later.

## Decision

- **URL.** `POST /hooks/flow/{token}` on the tenant's own host (`routes/flow-webhook.php`, no `web` group, `tenant`
  middleware), POST only. The token is 32 random bytes in base64url (43 characters), made by the server; it names the
  trigger and is shown to the editor in full. The tenant comes from the host; the token is looked up in the tenant's
  schema. This is a second inbound webhook path, owned by Flow (`App\Domains\Flow\Webhook`), not channel-ingress.
- **Endpoint and secret.** Table `flow_webhook_endpoints` in the tenant schema: its own ULID key, `tenant_id`, `flow_id`,
  unique `trigger_id`, unique `token`, `secret` encrypted with the application key, `secret_rotated_at`. The builder makes
  it before publish ("Get URL", `ManageFlowDefinitions` through the draft's `update` policy) only for a trigger the flow's
  draft lists as a webhook, and it stays bound to that flow. The secret is generated by the server or pasted from the
  sender (the draft's `publish` policy: who makes a trigger live hands out its secret), shown only in the answer
  that generated it, and never in the trigger's config: the validator refuses unknown keys, and a draft save drops a
  `secret` key. Making the URL and replacing the secret are audited.
- **Verification.** The trigger config holds only the scheme — `hmac_sha256` (header, prefix, optional signed string with
  `{raw}`, optional timestamp header and tolerance, the timestamp always inside the signed string) or `header_equals` —
  and becomes Foundation's `IngressSpec`, run by `IngressSpecExecutor`, the same code as channel webhooks. The query string
  is never read for a secret; `query_param` and `none` are not offered.
- **Once per delivery.** The delivery id comes from one placeholder (`{header.X}` / `{body.path}`, alternatives with `|`);
  the fire key is `wh:<id>`, or `wh:sha256:<hex>` when too long or not text. Redis `SET NX` for 24 h in front of the
  queue, released when dispatch fails, then the session's unique `(trigger_id, fire_key)` as the final guarantee. A
  request without an id gets a fresh ULID and no dedup (logged).
- **Live only when manageable.** A request is served only for a live, active `flow_triggers` row of type webhook of the
  endpoint's flow, whose flow has an active runnable definition and still has its draft and assistant. A publish that
  deletes a live webhook trigger or changes its type deletes its endpoint; deleting the flow deletes its endpoints.
- **Limits.** Unknown or dead tokens count against the tenant and address (60 a minute) before the lookup; a known token
  has the platform setting `flow.webhook.per_token_per_minute` (120). Body at most 256 KB. A stopped tenant answers 503
  with `Retry-After`.
- **Answer.** `response_mode: async` (the default): 202 once the run is queued (`StartAutomationRunJob`).
  `response_mode: sync`: after the dispatch, `FlowWebhookReceiver` holds the request for the flow's answer through
  `WebhookSyncWait` — only while it holds a slot of `WebhookWaitSlotsInterface` (Redis sorted sets scored by expiry,
  one Lua script for both levels: `flow.webhook.sync_waiters_max`, 5 on the installation, a quarter of the 20 PHP-FPM
  workers, and `flow.webhook.sync_waiters_per_tenant`, 2), for at most `flow.webhook.sync_wait_seconds` (1–30, 30).
  The answer travels through `WebhookReplyStoreInterface`: `SET NX EX 60` on
  `flow:webhook:reply:{tenant}:{trigger}:{sha256(fire key)}`, so the first answer of a run wins, and only the winning
  write pushes the wake-up the request `BLPOP`s on. It comes from the `webhook_response@1` node (status 200–499, JSON
  rendered leaf by leaf or text, at most 64 KB, keyed by the run root's `(trigger_id, fire_key)`, a no-op outside a
  webhook run) or, failing that, from `WebhookRunEndReply`, which `FlowEngine` calls wherever it stops running a
  session: a root automation run with a `wh:` fire key that has ended answers 200 completed / cancelled or 500 failed.
  No slot, no answer in time, or any Redis failure: 202. A repeated delivery gets the kept answer and never waits. No
  header of the answer comes from the flow.

## Alternatives

- **Base domain with a landlord token registry** (as channel webhooks): rejects bad tokens before entering a tenant and
  suits the Go gateway, but adds a landlord table written from Flow and its sync; the spec keeps webhooks off the gateway.
- **A user-chosen `path`.** Readable, but not unique in a tenant and guessable.
- **The secret in the trigger config.** Copied into every definition and template; the builder sends it to the browser.
- **Keep the secret in the credentials store** (`adr-20261119-credentials-store`). That store holds outbound secrets a `call` applies, each bound to its allowed hosts (D-1); an inbound verification secret has no host to bind, and it belongs to one endpoint, not to a shared set.
- **A hash of the secret.** HMAC needs the secret itself.
- **The body hash as delivery id.** Silently merges legitimate identical events.
- **A plain per-IP throttle.** Would cap a busy legitimate sender at the unknown-token rate.
- **Waiting without a ceiling, or a counter with a TTL as the ceiling.** Twenty waiting senders would take the whole
  PHP-FPM pool, the console of every tenant with it; a counter whose TTL every new slot refreshes never lets a slot
  leaked by a crashed request lapse under steady traffic.
- **Running the first segment inside the request, or polling the database for the run's end.** The first ties a web
  worker to a flow's `call`s; the second loads the database for every waiting second.

## Consequences

- A URL once handed out cannot change shape; rolling the code back leaves senders with dead URLs (404, retried).
- Secrets depend on `APP_KEY`, like channel tokens; changing it makes them unreadable and every sender must be given a new one.
- The `down()` of the migration drops the table with the secrets.
- Old webhook trigger configs (`method`/`path`/`secret`) never worked and no longer publish until re-set in the builder.
- Endpoints made for triggers never published stay as rows; they are never served.
- A `sync` answer is best effort: a burst, a queue backlog or the serialization of one trigger's runs turns it into
  202, and a run's later answer is lost after its minute in Redis.
