---
title: "Releases and versioning"
description: "How a change on main becomes a version an operator can install."
---

A release is a git tag on `main`. Nothing else: no release branch, no version
file to bump, no manual image build. The tag is pushed by the **Release tag**
workflow when the release notes pull request merges, so merging that pull
request is the act of releasing.

## Version numbers

Versions follow [Semantic Versioning](https://semver.org) and are written as
`vMAJOR.MINOR.PATCH` — `v0.4.2`, `v1.0.0`.

While the platform is pre-1.0 the rules are the `0.x` ones:

- **MINOR** goes up for new behaviour, and for anything that breaks an existing
  contract — a Flow node handler, the webhook format, the extension surface, a
  configuration key. Read the release notes before adopting a new minor.
- **PATCH** goes up for fixes that change no contract. A patch is always safe
  to take.

`1.0.0` is tagged when the public surface described in the
[stability policy](/extending/stability-policy) is one the project is prepared
to keep. From then on a breaking change raises MAJOR and nothing else does.

The tag is the only place the version lives. The container images read it from
the tag name at build time (`org.opencontainers.image.version`), and
`APP_VERSION` in an operator's environment refers to it directly.

## What a tag produces

A `v*` tag runs the **Publish images** workflow, which builds `core`,
`web` and `gateway` for amd64 and arm64 and pushes them to GitHub Container
Registry under every tag an operator might pin to, then publishes the GitHub
release for the tag. The Release tag workflow calls it directly after tagging;
a tag pushed by hand starts it on its own:

| Image tag  | From `v1.4.2`              | Moves?                       |
| ---------- | -------------------------- | ---------------------------- |
| `1.4.2`    | the full version           | never                        |
| `1.4`      | major.minor                | on each patch of 1.4         |
| `latest`   | the newest tagged release  | on every release             |
| `sha-…`    | the short commit hash      | never                        |

Operators who want upgrades to be a decision pin `1.4.2`; the
[upgrade guide](/self-hosting/upgrading) explains the rest.

## Cutting a release

Releases happen when a coherent piece of work is on `main`, not on a calendar.
A release every one or two weeks is normal for `0.x`; a release for a single
fix is fine too.

1. Make sure `main` is green and that any Dependabot pull requests you intend to
   include are merged.
2. Decide the number: did anything in `git log <previous-tag>..main` change a
   contract? Then MINOR, otherwise PATCH.
3. Open the release notes pull request. It is the last pull request of the
   release, cut from the current `main`, opened by an owner, member or
   collaborator of the repository, and titled `docs(release): ...` with the
   version in it, such as `docs(release): notes for v0.4.2`. Its **body**
   carries, each on lines of their own (the squash commit on `main` is the
   title and the body, so only the body reaches it), outside any HTML comment —
   the workflow ignores comments, as GitHub does not render them (a comment
   inside a fenced code block is kept; one in inline code is dropped):
   - `Release-Version: v0.4.2`;
   - `Release-Notes-Through: <sha>`, the full sha of the commit of `main` the
     notes describe. The project's agent tooling (`jig task ship`) also writes
     it into the branch commit; the body line is what survives a squash into a
     release epic;
   - the release text between a line `<!-- release-notes:start -->` and a line
     `<!-- release-notes:end -->`, with breaking changes and required operator
     actions (a migration, a new environment variable, a restart order) at the
     top, where they are impossible to miss. It is required: a release without
     it is refused rather than published with generated notes.
4. Merge it. The [Release tag](https://github.com/fapost-lab/core/actions/workflows/release-tag.yml)
   workflow waits for CI on the merged commit, pushes the annotated tag
   `v0.4.2` on it and runs Publish images. The GitHub release gets the text
   between the markers, exactly as it was when the workflow checked it: do not
   edit the body after the merge, or the release is not published.
5. Check that the run finished and the three images exist under the new tag.

A release epic, whose tasks ship together, is released by the pull request that
merges the epic into `main`. It is titled like a notes pull request
(`docs(release): ... v0.4.2`), and its body carries the same three things,
copied from the notes pull request: the `Release-Version:` line, the
`Release-Notes-Through:` line naming the commit of `main` merged into the epic
last, and the release text between the markers.

A pull request that reads like a release — a `docs(release)` title, a
`Release-Version:` or `Release-Notes-Through:` line, a release text marker —
is either a release or a refused one, never let through. The workflow refuses,
with a red run and no tag, whenever anything is in doubt: the title is not
`docs(release): ... vX.Y.Z`; the author is not an owner, member or
collaborator; no pull request is found for the commit; the version is malformed, stated twice differently, already tagged, not above
the latest tag, or not the next patch, minor or major after the latest release
(a pre-release of one is fine); the trailer is missing or does not name the merged commit's
parent, so something reached `main` that the notes do not describe; the
release text markers are missing or broken; or CI on the merged commit is not
green.
Fix the cause and re-run the failed jobs, or tag by hand.

Agents never push a tag. A maintainer tags by hand only for a maintenance
branch, or when the workflow refused a release that should go out as it is:

```bash
git switch main && git pull --ff-only
git tag -a v0.4.2 -m "v0.4.2"
git push origin v0.4.2
```

A tag pushed this way runs Publish images too. The release text is taken from
the merged pull request's markers when the tagged commit is one; otherwise, and
only for a tag pushed by hand, the release gets notes generated from the merged
pull request titles, to be edited with `gh release edit`. A release already
published for the tag is left as it is.

A pushed tag is not undone. If a release turns out to be broken, the fix is the
next patch tag, not a moved or deleted one — an operator may already have pulled
the image.

## Hotfixes

A fix for a released version is an ordinary `fix/` branch from `main`, merged
through a pull request and released as the next PATCH tag. Nothing about the
process is different; it is just done quickly.

The exception is the case where `main` already carries unreleased breaking
changes and an operator on the previous minor needs the fix without them. Then,
and only then, a maintenance branch is created from the released tag:

```bash
git switch -c release/1.4 v1.4.2
git cherry-pick <merged fix commit from main>
git tag -a v1.4.3 -m "v1.4.3"
git push origin release/1.4 v1.4.3
```

The fix lands on `main` first and is cherry-picked back, never the other way
round, so that `main` can never be missing a fix a release has. Maintenance
branches are created on demand and deleted once the minor they serve is no
longer in use. Before 1.0 this case is not expected to arise.

## Pre-releases

A change that wants operator feedback before it is called a release is tagged
`v1.5.0-rc.1`. It builds images like any other tag, but `latest` is not moved
to it, and the release the workflow publishes is marked as a pre-release.
