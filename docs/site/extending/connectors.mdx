<Warning>
  Experimental. A connector's channel can be created in the console and receives and
  sends messages, but its settings form is a generic list of keys and values until
  connectors can describe their own fields.
</Warning>

A connector brings one or more messaging channels — Telegram, Viber — to an
installation. It is a Composer package, installed when the image is built, like a
[Solution](/extending/solutions). Unlike a Solution it is not activated per tenant:
once installed, its channel types exist for the whole installation, and which tenant
may use them is the operator's decision.

## The manifest

A connector describes itself in its own `composer.json`: `"type": "fapost-connector"`
and an `extra.fapost` block. Core reads it on `platform:update` without running your code.

```json
{
  "name": "acme/fapost-connector-viber",
  "type": "fapost-connector",
  "require": { "fapost/foundation": ">=0.21 <1.0" },
  "extra": {
    "fapost": {
      "schema": 1,
      "id": "viber",
      "name": "Viber",
      "description": "Viber bots through the REST Bot API.",
      "provider": "Acme\\ConnectorViber\\ViberConnectorServiceProvider",
      "channels": ["viber"]
    }
  }
}
```

| Field | Required | Rule |
|---|---|---|
| `type` | yes | `fapost-connector` |
| `extra.fapost.schema` | yes | An integer; `1` is the only supported number |
| `extra.fapost.id` | yes | The same rule as a Solution's id. Ids are one space: a connector's id may not equal any installed Solution's or connector's |
| `extra.fapost.name` | yes | One line, 1 to 60 characters, in English |
| `extra.fapost.description` | no | Up to 280 characters |
| `extra.fapost.provider` | yes | The class name of your service provider; it must exist and extend `Fapost\Foundation\Lifecycle\AbstractConnectorServiceProvider` |
| `extra.fapost.channels` | yes | A non-empty list of unique channel types, each `^[a-z][a-z0-9_]{1,31}$`. A channel type belongs to one connector only |
| `extra.fapost.x-*` | no | Ignored; for your own tooling |
| `extra.laravel.providers` | no | Must be absent or empty: Core boots your provider |
| `require.fapost/foundation` | yes | A constraint; `fapost/core` may not be required |

Any other field is an error. When two packages claim one id, or two connectors one
channel type, none of them is booted and `platform:update` stops with nothing changed.

The rules live in Foundation (`Fapost\Foundation\Connector\Manifest\ConnectorManifestParser`),
a pure function you can run in your package's CI.

## The service provider

```php
final class ViberConnectorServiceProvider extends AbstractConnectorServiceProvider
{
    protected function registerChannels(ConnectorRegistrarInterface $registrar): void
    {
        $registrar->registerChannel(new ConnectorChannel(
            type: 'viber',
            sender: ViberSender::class,
            inbound: ViberInboundAdapter::class,
            webhookRegistrar: ViberWebhookRegistrar::class,
            mediaLinkPolicy: ViberMediaLinkPolicy::class,
            capabilities: new ChannelCapabilities([
                ChannelCapability::CallbackButtons,
                ChannelCapability::ReplyButtons,
            ]),
        ));
    }
}
```

Core calls `registerChannels()` once per process, after every provider's `register()`
and before any `boot()`. `registerBindings()` runs in `register()`, `bootConnector()`
in `boot()`. Core boots connectors before Solutions.

A `ConnectorChannel` names classes, not instances: Core builds each service inside the
request or job that uses it and never shares one across requests or jobs, so a service
may depend on tenant-scoped bindings. Core also builds one instance at boot to check
it, so constructors must be cheap and must not touch tenant data.

| Field | Required | Implements |
|---|---|---|
| `type` | yes | A channel type listed in `extra.fapost.channels` |
| `sender` | yes | `Fapost\Foundation\Messaging\ProviderSenderInterface` |
| `inbound` | yes | `Fapost\Foundation\Channel\ChannelInboundAdapterInterface` |
| `webhookRegistrar` | no | `Fapost\Foundation\Channel\WebhookRegistrarInterface` |
| `mediaUploader` | no | `Fapost\Foundation\Media\ChannelMediaUploaderInterface` |
| `mediaDownloader` | no | `Fapost\Foundation\Media\ChannelMediaDownloaderInterface` |
| `mediaLinkPolicy` | no | `Fapost\Foundation\Media\ChannelMediaLinkPolicyInterface` |
| `capabilities` | no | A `Fapost\Foundation\Messaging\ChannelCapabilities` listing what the channel can do beyond text and media |

Boot fails, naming your connector, when you register a type your manifest does not
declare, a type Core serves itself (such as `telegram`), a type twice, a class that does
not implement its interface, or a media class whose `channelType()` is another type.
`platform:update` also refuses a declared type you never register.

## Buttons and capabilities

A channel that declares no `capabilities` is text and media only, and Core sends it
nothing else. Declare what the channel can do with `ChannelCapability`:
`CallbackButtons`, `ReplyButtons`, `ShareContact`, `ShareLocation`, `RemoveButtons`
(strip the buttons of a message already sent) and `PersistentButtons` (callback buttons
of older messages stay pressable).

Core describes the buttons of a message by what a press does, not by where a channel
draws them: `MessagePayload::$buttons` is a `ButtonSet` of rows of `Button`. Each button
has a `label` and an action: `Callback` (the press returns a hidden payload),
`Reply` (the press sends the label as the user's message), `ShareContact` or
`ShareLocation`. A set holds either callback buttons only or none. Translate it into the
provider's format in your sender. Core's flow messages carry `buttons` and leave
`MessagePayload::$keyboard` null; `keyboard` is deprecated, so a sender that reads only
it shows no buttons.

When the user presses a `Callback` button, report it as an `IncomingMessage` of type
`IncomingMessageType::CallbackQuery` whose `text` is the button's payload, unchanged.
How the provider delivers the press is the connector's business. The payload is at most
`Button::MAX_PAYLOAD_BYTES` (64) bytes and Core treats it as opaque to you.

## Inbound webhooks

The inbound adapter does not verify signatures in code. It declares how in an
`IngressSpec`, which Core and the ingress gateway both execute, and turns a verified
body into an `IncomingMessage` in the worker:

```php
final class ViberInboundAdapter implements ChannelInboundAdapterInterface
{
    public function ingressSpec(): IngressSpec
    {
        return IngressSpec::hmacSha256('x-viber-content-signature', 'viber:{channel}:{body.message_token}');
    }

    public function normalize(array $payload): IncomingMessage
    {
        // map the provider's payload to an IncomingMessage
    }
}
```

If your provider signs requests in a way no `SignatureScheme` covers, the scheme is
extended in Foundation and the gateway; a connector cannot ship its own check.

## When a connector is removed

Channels of a type no connector serves any more stay in the database untouched. The
console marks them unavailable and lets you delete them; their incoming webhooks are
logged and acknowledged without being processed, and `php artisan platform:update`
lists them per tenant. Installing the connector again brings them back.

## Installing

Add the package to your image through the build overlay
([Building your own images](/self-hosting/docker-compose#building-your-own-images)), then run
`php artisan platform:update`: it lists the installed connectors with their channel
types, or refuses with every manifest problem it found.
