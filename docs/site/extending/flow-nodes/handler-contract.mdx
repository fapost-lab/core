---
title: "Handler contract"
description: "What a node handler receives and what it must return."
---

A node handler is the runtime behaviour behind one kind of node on the flow
canvas. It implements `Fapost\Foundation\Contracts\NodeHandlerInterface`.

```php
interface NodeHandlerInterface
{
    public function type(): string;
    public function version(): int;
    /** @return int[] */
    public function supportedVersions(): array;
    public function label(): string;
    public function category(): string;
    /** @return array<string, mixed> */
    public function configSchema(): array;

    public function execute(
        array $nodeConfig,
        array $state,
        NodeExecutionContext $context,
    ): NodeExecutionResult;
}
```

## Identity

`type()` is the node's unique identifier, such as `send_message`. It must be
unique across every registered handler, including those from other extensions:
a Solution's types start with its id and a dot (`feedback.collect`), which Core's
never contain.
`version()` is the handler's current version; the engine resolves a handler by the
pair `(type, version)` from an in-memory registry, with no database query on the
hot path.

`label()` and `category()` are what the builder shows: the node's name and the
group it appears under. The group is a value of
`Fapost\Foundation\Flow\Enums\NodeCategory` or, for a Solution's node, the
Solution's id — see [Registering node types](/extending/solutions#registering-node-types).

Override `category()`: the default of `AbstractVersionedHandler`, `Core`, is not a palette group, so a handler
that keeps it fails the boot. That default is deprecated and becomes abstract in Foundation 1.0.

## Configuration

`configSchema()` returns the schema the builder uses to validate the node and draw
its form. This is the mechanism that lets an extension be configurable without
shipping any front-end code — see [Builder UI extensions](/extending/builder-ui).

## Execution

`execute()` receives three things:

| Argument | What it is |
|---|---|
| `$nodeConfig` | The node's payload from the flow definition JSON: `id`, `type`, `version`, `config`, and so on |
| `$state` | Namespaced session state, **read-only** for the handler |
| `$context` | `NodeExecutionContext` — tenant, contact, and session metadata, plus the writers a handler is allowed to use |

A flow started by a schedule, a webhook or an API call runs without a contact. A node needs a contact unless its
handler says otherwise, so such a flow cannot be published while it holds your node; nodes in flows started by a
message or an event are unaffected. A handler that can run without a contact implements
`Fapost\Foundation\Flow\Contracts\DeclaresContextRequirementInterface`:

```php
use Fapost\Foundation\Flow\Contracts\DeclaresContextRequirementInterface;
use Fapost\Foundation\Flow\Enums\NodeContextRequirement;

final class TickHandler extends AbstractVersionedHandler implements DeclaresContextRequirementInterface
{
    public function contextRequirement(): NodeContextRequirement
    {
        return NodeContextRequirement::Any;   // or None: never uses a contact
    }

    // type(), version(), category(), execute() …
}
```

On a run without a contact, `$context->contactId` and `$context->platform` are `null`, reading `contact.*` or
`module.*` through the state reader throws, and so does every write through the contact writer. A node whose config
reads the contact or uses a contact variable is refused in such a flow whatever its handler declares. The interface
needs `fapost/foundation` `^0.42`.

`execute()` returns a `NodeExecutionResult`, built through one of its named constructors:

```php
NodeExecutionResult::executed(sourceHandle: 'default', stateChanges: [
    'flow.answer' => $value,
]);

NodeExecutionResult::waiting();   // the flow pauses for input
NodeExecutionResult::delayed();   // pauses like waiting() — see below
NodeExecutionResult::delayed(resumeAt: $when);   // pauses until a specific time
```

`delayed()` has two forms:

| Call | Session | Contact message meanwhile | When the handler runs again |
|---|---|---|---|
| `delayed()` | `waiting_input`, same as `waiting()` | runs your handler again | with the next inbound message |
| `delayed(resumeAt: $when)` | `paused` | answered with the assistant's busy notice, not delivered to your handler | at `$when` (a queued wake-up), or with the first message after it |

Without `resumeAt`, the session waits exactly as after `waiting()`: the
contact's next message runs your handler again, and the handler decides
whether it is time to move on — the built-in `delay` node works this way.
Nothing wakes the node without an inbound message.

With `resumeAt`, nothing the contact sends reaches your handler until that
time: the engine wakes the node itself, and only then does the flow resume.
Your handler tells the two situations apart through
`NodeExecutionContext::$resumedAfterDelay` — `true` only on the run the engine
triggered for this `resumeAt`, `false` on every other call, including the one
that first asked for it:

```php
public function execute(array $nodeConfig, array $state, NodeExecutionContext $context): NodeExecutionResult
{
    if ($context->resumedAfterDelay) {
        // The engine woke this node at the time it asked for — move on.
        return NodeExecutionResult::executed();
    }

    return NodeExecutionResult::delayed(resumeAt: now()->addHour());
}
```

<Warning>
  Do not read the `resume_at` you asked for back out of `$state`. The marker
  the engine uses to schedule and match the wake-up is an internal detail, not
  part of the handler contract, and may change — rely on `$resumedAfterDelay`.
</Warning>

### Data for the run trace

Every node writes a trace row when it completes. In an automation run that row holds the node's input (the incoming
message) and output (state changes and result metadata). A handler can add what only it knows (the request it sent,
the response it received) through the `trace` argument of `NodeExecutionResult`:

```php
return new NodeExecutionResult(
    status: NodeExecutionStatus::Executed,
    sourceHandle: 'success',
    stateChanges: ['flow.order' => $order],
    trace: [
        'input'  => ['endpoint' => $endpoint, 'query' => $query],
        'output' => ['status' => $status, 'body' => $body],
    ],
);
```

The trace is written nowhere else: not to the flow log, not to the session state. Core masks values under sensitive
key names (`authorization`, `password`, `token`, `api_key`, `secret` and the like), passwords and sensitive query
parameters in URLs, and cuts a row to 1 MB. Masking goes by key name, not by content, so never put a raw secret under
an innocent name. A conversation's trace keeps no input or output. `trace` needs `fapost/foundation` `^0.44` and is
experimental.

## The handler must be graph-unaware

<Warning>
  A handler returns a `sourceHandle`, never the id of the next node.
</Warning>

The engine resolves what comes next from the flow's edges, using the source node
id together with the handle the handler returned. A handler that decides which
node runs next has taken a decision that belongs to the flow definition, and the
same handler can then no longer be reused in a differently-shaped flow.

`sourceHandle` defaults to `'default'`. A node with several outcomes — a branch, a
validation that can fail — returns a different handle per outcome, and the person
building the flow wires each handle where they want it to go.

## Writing outside the session

State changes go back through `stateChanges` on the result. Mutations that live
outside the session JSON — contact attributes, contact language — are performed by
the handler through the writer it receives on `NodeExecutionContext`, such as
`ContactWriterInterface`.

<Warning>
  Do not return a legacy `effects[]` array. It was removed; handlers use the
  writer or port from the execution context instead.
</Warning>
