A Solution is a vertical product module — HR, recruitment, anything with its own
domain behaviour — distributed as a Composer package under your own vendor.

<Note>
  The external Solution lifecycle is partly built in Core. The manifest below is
  read and validated by `platform:update` today, and a tenant's activation of a
  Solution is stored and switched with `solutions:activate` and `solutions:deactivate`;
  the registrar that mounts what a Solution declares, the activation screen and the
  release tooling around them are still being built. Treat this page as the contract you will be held to,
  not as a finished walkthrough.
</Note>

## Boundaries

A Solution must not live under `app/Solutions` inside Core. It is an external
package, resolved through Composer like any other dependency — see
[Development setup](/extending/development-setup) for the two-lane workflow.

Its public contracts belong in `fapost/foundation`. Primitives with no Core
dependency belong in `fapost/support`. Neither package may reference `App\…`, and neither may
absorb business logic that belongs to Core.

Front-end components are possible, but only through the agreed build and publish
contract. A Solution cannot drop Vue files into a running application — the
builder front end is compiled ahead of time.

## The manifest

A Solution describes itself in its own `composer.json`: `"type": "fapost-solution"` and an
`extra.fapost` block. It is data, so Core can check it without loading your code, and the check
fails on the deploy, not on a customer's request.

```json
{
  "name": "acme/fapost-feedback",
  "type": "fapost-solution",
  "require": { "fapost/foundation": "^0.13" },
  "extra": {
    "fapost": {
      "schema": 1,
      "id": "feedback",
      "name": "Feedback",
      "description": "Collect and route customer feedback from flows.",
      "provider": "Acme\\Feedback\\FeedbackServiceProvider",
      "actions": ["feedback.submit", "feedback.score"]
    }
  }
}
```

The version is the package version Composer already knows, and the Foundation range is the
package's `require`; neither is repeated in the manifest.

| Field | Required | Rule |
|---|---|---|
| `type` | yes | `fapost-solution` (`fapost-plugin` is reserved) |
| `extra.fapost.schema` | yes | An integer; `1` is the only supported number |
| `extra.fapost.id` | yes | `^[a-z][a-z0-9_]{1,31}$`, and not `core`, `platform`, `fapost`, `app`, `system`, `flow`, `module`, `rag`, `solution` or `solutions` |
| `extra.fapost.name` | yes | One line, 1 to 60 characters, in English |
| `extra.fapost.description` | no | Up to 280 characters |
| `extra.fapost.provider` | yes | The class name of your service provider; the class must exist and extend `Fapost\Foundation\Lifecycle\AbstractSolutionServiceProvider` |
| `extra.fapost.actions` | no | The action ids you register, each starting with `<id>.`, no duplicates |
| `extra.fapost.x-*` | no | Ignored, for your own tooling |
| `require.fapost/foundation` | yes | The Foundation range you need; Composer enforces it when the package is installed |
| `require.fapost/core` | forbidden | A Solution depends on contracts, never on Core |

`solution` and `solutions` are reserved from `fapost/foundation` 0.14; use neither, whatever version
you build against, because Core's own tables carry that prefix.

**The id never changes.** Plans, activations, action ids, permissions and limits all hang on it. A
different id is a different Solution, and moving a customer's data across is your job.

**List your actions.** The prefix `<id>.` keeps your handlers from colliding with another Solution's,
or with `core.*` and `platform.*`. Declaring them lets Core show what your Solution offers without
loading it.

**Do not use `extra.laravel.providers`.** Core boots the provider named in the manifest itself, and
only for a Solution whose manifest is valid; Laravel's package discovery would boot any provider
listed there regardless. Any entry is a manifest violation (`extra.laravel.providers: a Solution's
provider is booted by Core; remove this block`); an empty list is accepted.

### Activation

Installing a Solution does not turn it on. Activation belongs to a tenant and is stored in that tenant's
own schema, so it goes with the tenant's backup and is removed with the tenant.

- A Solution is **off by default** for every tenant, new or existing, until it is activated.
- It counts as active only while the tenant has it activated **and** it is installed in the image with a
  valid manifest. Remove the package, or break its manifest, and it is inactive for every tenant; bring it
  back and it is active again where the tenant had left it on. Nothing is written in between.
- Deactivating never touches the Solution's data. The activation record stays, and every change is
  journalled with who made it, when, and why.
- A change is seen by the next request or job of any process; a job already running keeps the answer it
  was given at its first question.

An operator switches it with `solutions:activate` and `solutions:deactivate`, each with a required
`--tenant=<slug>`; see the [command reference](/reference/artisan-commands#solutions).

### Checking it

```bash
php artisan platform:update --validate-only
```

Prints every problem, not just the first, and exits with code 1:

```
acme/fapost-feedback: extra.fapost.id: required
acme/fapost-feedback: extra.fapost.actions[1]: "score" must start with "feedback."
acme/fapost-feedback: extra.fapost.migrations: unknown field (schema 1 allows: schema, id, name, description, provider, actions); a newer fapost/foundation may be required
acme/one, acme/two: extra.fapost.id: "feedback" is declared by both packages
```

A package with a wrong manifest, and both packages when two share an id, are left out of the
catalog. The same check runs at the start of every `platform:update`, before any migration. See
[Upgrading and rollback](/self-hosting/upgrading#solutions-are-checked-first).

Without Core, for example in your package's own CI, run the same rules from `fapost/foundation`:

```php
use Fapost\Foundation\Solution\Manifest\ManifestParser;

$result = (new ManifestParser())->parse(json_decode(file_get_contents('composer.json'), true));

$result->isValid();
$result->lines();
```

### How the format changes

Unknown fields are an error, except `x-*`, so a Solution written for a newer platform never
installs quietly without part of its behaviour. A new optional field arrives in a minor release of
`fapost/foundation`; to use it, require that version, and Composer then refuses to install your
Solution on a platform that does not have it. A breaking change gets a new `schema` number;
Foundation reads the current schema and the previous one within one major version, and refuses
anything else. A field not in schema 1 yet, for example the UI of a Solution or its migrations, is
added the same way when its contract is settled.

## Limiting what a tenant can create

If your Solution has records an operator should be able to cap per tenant (for example candidates),
register a limit key from your service provider's `boot()`. Core binds the registry in its own
provider, which can run after a package's `register()`, and closes the registry once the application
has booted, so do not register from `register()` or from a `booted()` callback:

```php
use Fapost\Foundation\Quota\Contracts\LimitRegistryInterface;
use Fapost\Foundation\Quota\DTO\LimitDefinition;
use Fapost\Foundation\Quota\Enums\LimitKind;

$this->app->make(LimitRegistryInterface::class)->register(new LimitDefinition(
    key: 'candidates',
    label: 'Candidates',
    unit: 'candidates',
    kind: LimitKind::Records,
));
```

The key is `snake_case` and stable, because plans store limits under it; the label and unit are in
English. An operator package reads the registry to offer the limit in its plan form, and answers how
much each tenant may have through `TenantLimitsInterface`. Registering the key is the Solution's
whole contribution to the contract: it does not decide the number.

Registering the key makes the limit exist; enforcing it is your Solution's job. Create the records
through one service that counts the tenant's existing ones and asks `RecordQuotaInterface` before
saving, and send every creation path through that service:

```php
use Fapost\Foundation\Quota\Contracts\RecordQuotaInterface;

$this->recordQuota->assertCanCreate('candidates', Candidate::query()->count());
```

It throws `RecordLimitReachedException` with a message fit for the person who sees it; catch it
where you show errors. It works in the tenant context of the current request or job. Records that
already exist stay when a limit drops: only creating more is refused. See
[Foundation contracts](/reference/foundation-contracts#quota) for the interfaces.

### Limiting how much a tenant does in a period

For work that is counted over time rather than stored, such as messages sent or calls made, register
the key from `boot()` the same way with `kind: LimitKind::PerPeriod`. Nothing is stored in a tenant
schema; the operator package counts. Spend one unit before the work, with a natural key that is the
same on every retry, and do the work only when the answer is allowed:

```php
use Fapost\Foundation\Quota\Contracts\UsageMeterInterface;
use Fapost\Foundation\Quota\DTO\UsageUnit;

$decision = $this->meter->consume(new UsageUnit($tenantId, 'candidate_imports', "import:{$importId}", $startedAt));

if (! $decision->allowed) {
    // Not done, and not retried: the limit holds until the period ends.
}
```

Core wraps this call to fail open when the operator's implementation throws; your code is calling the
interface directly, so catch `Throwable` around it, report it and let the work through, which is what
Core does. Build the `UsageUnit` before anything irreversible, and never put a personal identifier in
the unit key. See [Foundation contracts](/reference/foundation-contracts#counting-use-over-a-period)
for what the implementation promises.

## Before you start

Read [Choosing an extension type](/extending/choosing-an-extension-type) first. The
most common mistake is building a Solution for something that has no domain of its
own and should have been a Plugin — or, more expensively, building one for
something that belongs in Core.
