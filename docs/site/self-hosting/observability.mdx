Most failures in FaPost are silent by nature. A provider that cannot reach you
does not complain; a queue that is not being worked simply grows. Knowing where
to look matters more than having alerts on everything.

## Horizon

Queues are processed by Horizon, and its dashboard is the first place to look
when messages arrive but nothing happens.

Four supervisors run, grouped so that the latency-critical work is isolated:
inbound processing and conversation replies share dedicated processes, while
broadcasts, logging and background synchronisation are worked elsewhere. See
[Queues](/reference/queues).

On a `single` installation the dashboard is at `/horizon` for signed-in staff who hold the
**View operator screens** permission; administrators hold every permission. The platform
support user does not open it, whatever its role. Grant the permission to a custom role
in the console's role form when someone who is not an administrator should see the queues.

In `host` tenancy mode the dashboard is served on the base domain and on declared
platform subdomains only, never on a tenant's host, and Core keeps it closed for everyone,
tenant administrators included, until an operator package answers for it; see
[Several tenants](/self-hosting/docker-compose#several-tenants-host-mode).

What to watch:

- **Wait time on `flow.execution`** — this is how long a contact waits before the
  assistant even begins. It should be near zero.
- **Failed jobs** — a rising count on `flow.execution` means inbound messages are
  not being answered: replies are sent from inside that job.
- **Throughput on `messaging.broadcast`** — expected to spike; it is the one
  queue whose depth is not alarming.

<Warning>
  An installation without Horizon running accepts messages and never answers
  them. Everything looks healthy from the browser — the site serves, the panel
  works — because nothing about the web tier depends on the workers. See
  [Services](/self-hosting/services).
</Warning>

## The scheduler

Five scheduled tasks matter, and all fail silently if the scheduler is not
running:

| Task | When | If it does not run |
|---|---|---|
| `flow:sweep-subflow-timeouts` | Every minute | Parent flows waiting on expired subflows never resume |
| `logs:create-partition` | Monthly, on the 1st | Next month's flow-log partition is missing |
| `logs:prune-flow` | Daily, 03:00 | Old log partitions accumulate |
| `conversations:prune` | Daily, 03:15 | Nothing is pruned; the transcript keeps growing (a no-op while retention is `0`) |
| `horizon:snapshot` | Every five minutes | Horizon's metrics and the health page's jobs-per-minute figures stop moving |

The monthly one is the trap: it fails at a month boundary, weeks after the
scheduler stopped, and presents as flow logging breaking for no apparent reason.

## Conversation retention

The conversation transcript is kept forever by default. To cap it, set
the platform setting `conversation.retention_days` (a number of days, `0` keeps
forever) in [Platform settings](/self-hosting/platform-settings), or in host mode with
`php artisan platform:settings:set conversation.retention_days 90`.
`CONVERSATION_RETENTION_DAYS` in `.env` is only its default. The daily `conversations:prune` task then
drops, in every tenant schema, the monthly `conversation_messages` partitions that
lie wholly older than that many days. Whole months only, so a message lives between
that many days and about 31 days longer.

<Warning>
  Pruning is irreversible. A dropped partition is gone for good; only a database
  backup brings it back. Preview first with
  `php artisan conversations:prune --dry-run`.
</Warning>

Conversation threads (the inbox rows and their metadata) and downloaded media are
not touched. With the variable unset the task does nothing.

## Webhook routing

Inbound routing resolves through Redis rather than the database, which makes the
registry a cache with a source of truth behind it — and caches drift.

```bash
php artisan ops:webhook-registry-health
```

Reports and optionally repairs inconsistency between Redis and the database.

```bash
php artisan ops:webhook-warmup
```

Rebuilds the registry from the database. Run it after a Redis flush, a restore,
or a move to new Redis infrastructure — without it, channels exist and no message
resolves.

```bash
php artisan gateway:doctor
```

Checks the ingress end to end: which driver is active, whether Redis is
reachable, whether the key prefix matches, whether published specs agree with the
adapters, and how many channels still point at a previous address. Run it first
whenever webhooks are not arriving.

## Health page

The admin panel has a **System → Health** page, open to anyone with the "View system" permission
(administrators have it). On an installation that serves a single organisation it shows whether live updates,
webhook intake and the background queues work right now.

On a multi-tenant installation (`host` mode) the page is there for a tenant's users with the same permission, but it
shows only that tenant's slice: the state of live updates (Reverb) and the number of the tenant's open live channels,
and the state of the webhook gateway and how many of the tenant's channels are still on the old address. There are no
connection counts, addresses, published specifications, reasons or a Queues card, because those belong to the whole
installation. The sections below describe the full page of a single-organisation installation.

The page asks again every 15 seconds over plain HTTP, never over Reverb, so it
keeps working when the websocket is what has failed. Each of its three cards,
**Live updates** (Reverb), **Webhook gateway** and **Queues** (Horizon), is in exactly one state:

| State | What it means |
|---|---|
| **Up** | The service answered and reported itself healthy. This is the only green state. |
| **Down** | The service answered, and what it said is that it is not healthy. |
| **Unknown** | The check could not be completed: the service is unreachable from the application, rejected the request, or the settings needed to ask it are missing. The card says which. This is not the same as down, and the page never shows it as healthy. |
| **Switched off** | The service is off on purpose: `BROADCAST_CONNECTION` is not `reverb`, the webhook ingress driver is `laravel`, or `QUEUE_CONNECTION` is not `redis`. Nothing is wrong. |

While the first answer is on its way, the cards show a loading state. If a
refresh fails, the page keeps the last answer on screen, marks it as out of
date, and keeps trying.

The Reverb card also shows the connections and channels Reverb holds. The
gateway card shows the address the application asks, whether the published
specifications agree with the adapters, and how many channels still deliver to the
address they were registered with. A channel on an old address keeps working,
more slowly, so it is a figure to read and not a reason to call the gateway down.

The Queues card reads Horizon's own metrics. It is **up** while Horizon is running
and **down** when no Horizon instance has reported in or all of them are paused, since
queued jobs are then not being processed. It is **unknown** when Redis cannot be
read, and **switched off** when `QUEUE_CONNECTION` is not `redis`. For each named
queue it shows how long the queue would take to clear, highlighted with the words
"Long wait" once it reaches Horizon's long-wait threshold (`horizon.waits`, 60
seconds unless set), and the jobs per minute processed since the last Horizon
snapshot. A queue that no running supervisor serves shows no wait rather than a
zero. The card also counts failed jobs over Horizon's recent-failed window
(`horizon.trim.recent_failed`, 7 days by default). The per-minute figures depend on
the `horizon:snapshot` task above: the card says when the current window began, with
the date when it is not today, so a window that has stayed open for days shows it.

## Per-assistant health

Each [assistant console](/using/console-overview) shows two counters that should
stay boring: **live sessions** and **errors in the last 24 hours**.

Live sessions climbing without traffic to explain it means conversations start
and do not finish — usually a flow waiting at an input nobody answers. Errors
above zero means at least one node failed; [Flow logs](/using/flow-logs) says
which.

## Application logs

Laravel's log carries application errors. Telescope is available in development
and records every request with its contents — which is why it must be off in
production.

## Backpressure

Provider rate limits are handled preventively rather than as a reaction to being
rejected. The relevant settings are per-tenant: message rate per chat, broadcast
chunk size, and how hard the platform pushes when a provider strains.
A tenant admin sets them under Tenant settings. The message rate per chat is
picked up by the next job without a restart; every tenant starts at 30 per minute.
`MESSAGING_RATE_LIMIT_PER_MINUTE` no longer sets a tenant's rate — it is only a
fallback for sends outside a tenant.

A provider complaining about rate is a signal to lower those, not to add
retries — a retry storm against a limit is the same request made worse.
