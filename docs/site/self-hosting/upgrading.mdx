What changes between releases and in what order to apply it.

## The shape of an upgrade

Four things happen, and the order is not interchangeable:

1. New code arrives (new image, or new checkout plus `composer install`)
2. The installed Solutions are checked, ideally with `platform:update --validate-only` before the running containers are replaced: a manifest that is wrong stops the upgrade here, before anything is changed
3. **Landlord** migrations run — platform-wide tables, including any that an operator package (SaaS, monitoring) adds — and then **tenant** migrations, once per tenant schema
4. Queue workers restart, so they stop running the previous release from memory

`php artisan platform:update` repeats the check and does step 3 in one command, then publishes the Solutions'
[console UI](/extending/console-ui#publication) and caches the catalog of installed Solutions. Step 4 stays yours.

Step 4 is the one most often forgotten. Horizon workers are long-lived PHP
processes: until they are restarted they keep executing the old code against the
new database schema, which is the worst combination of the two.

## Docker Compose

```bash
docker compose pull
docker compose run --rm app php artisan platform:update --validate-only   # new image, old containers still running
docker compose up -d

docker compose exec app php artisan platform:update

docker compose exec app php artisan horizon:terminate
```

`horizon:terminate` lets in-flight jobs finish and then exits; Compose restarts
the container with the new image. Killing workers outright drops whatever they
were processing — and for an inbound webhook that means a message the provider
already considers delivered.

Pin a version rather than tracking `latest` if you want upgrades to be a decision
rather than an event:

```dotenv
APP_VERSION=1.4.2
```

The console footer shows the release the running image was built from, next to
"Powered by FaPost", so after an upgrade you can see it took. An image you build
yourself with `docker/compose.build.yaml` shows the `APP_VERSION` it was built
with, or `dev` without one.

## Solutions are checked first

A Solution is a Composer package whose `composer.json` carries a manifest (see
[The Solution manifest](/extending/solutions#the-manifest)). `platform:update` reads the manifest of
every installed Solution before it touches the database. If any is wrong it prints one line per
problem, for example

```
acme/fapost-feedback: extra.fapost.id: must match ^[a-z][a-z0-9_]{1,31}$
```

changes nothing and exits with code 1. A package with a wrong manifest, and both packages when two
declare the same id, are not used by Core even if you start it anyway. To check without upgrading,
for example in a pipeline or when building a derived image:

```bash
php artisan platform:update --validate-only
```

The same step checks that every action a manifest declares in `extra.fapost.actions` is registered by
the Solution's provider. A declared action nobody registered is reported as
`acme/fapost-feedback: extra.fapost.actions[1]: "feedback.score" is declared but not registered`, and
`platform:update` (also with `--validate-only`) exits with code 1 before anything is migrated.

This needs no database. After a successful update the catalog of Solutions is cached in
`bootstrap/cache/fapost-solutions.php`; if that file is missing or older than the installed
packages, Core builds the catalog from the package files instead, so a stale cache cannot hide a
Solution.

<Warning>
  A Solution that breaks the registration rules (an action its manifest does not declare, a duplicate
  action id, an unsupported registrar call) stops the application from booting: the web process,
  Horizon and every `php artisan` command fail, including `package:discover` during `composer install`
  and `platform:update` itself. Fix the package or remove it from the image; the message names the
  Solution, the package, the action and the class.
</Warning>

## Two schemas, two migration commands

`platform:update` runs both of the commands below, in that order. They remain available on their
own. Tenant isolation is schema-per-tenant, so a migration touching tenant tables must
run once per tenant. `ops:tenants-migrate` iterates active tenants and runs each tenant's schema
migrations and then its settings migrations; plain `artisan migrate` does not and will leave every
tenant schema untouched.

A release can contain either kind or both. Running both commands unconditionally
is safe — an already-applied migration is skipped.

## Before upgrading

**Back up the database.** Migrations are not reversible in practice: `down()`
methods exist but are exercised far less than `up()`, and a partial rollback on a
schema-per-tenant layout is worse than a restore.

```bash
docker compose exec postgres \
  pg_dump -U fapost fapost | gzip > backup-$(date +%F).sql.gz
```

**Read the release notes for breaking changes**, particularly any that touch
Flow node contracts. A node handler's contract is versioned: existing flow
definitions keep running against the old version, but a release may add a new one
that new flows use.

## Moving to host mode

Switching `TENANCY_RESOLUTION` from `single` to `host` changes which hosts the
application answers, so do it deliberately:

1. Set up the wildcard DNS record and certificate first
   ([Several tenants](/self-hosting/docker-compose#several-tenants-host-mode)).
2. Make sure `SESSION_DRIVER` is not `database` and `SESSION_DOMAIN` is unset. Sessions
   stored by the old driver are not carried over, so everyone signs in again.
3. Put `WEBHOOK_BASE_URL` and the gateway host under `TENANCY_BASE_DOMAIN`. A host
   outside it gets 400, and channels registered against such a host stop receiving.
4. Set `TENANCY_RESOLUTION=host`, then recreate the containers so the route cache is
   rebuilt: `docker compose up -d --force-recreate app horizon scheduler`.

The existing tenant keeps its slug and is served at `<slug>.<base domain>`; the base
domain stops serving the panel. Going back to `single` is the same edit the other way.

## Trusted proxies

`TRUSTED_PROXIES` is new. Compose installations get a default that trusts only the
bundled Caddy at its fixed address on the compose network, which makes the client
address correct behind it and changes what rate limits see: they now count real
clients instead of one. The Compose file now also defines the network's subnet
(`172.30.0.0/24`, dynamic addresses from `172.30.0.128/25`); set `COMPOSE_SUBNET`,
`COMPOSE_IP_RANGE` and `CADDY_ADDRESS` together if that collides with something on your
host, and give a second installation from the same file (a staging `ENV_FILE`) its own
values. Because the network definition changed, recreate it once:
`docker compose down` and then `docker compose up -d`. Bare metal and other setups trust nobody until the variable
is set, as before.

## Conversation settings move to the admin

`CONVERSATION_LOGGING`, `CONVERSATION_MEDIA_FETCH` and `CONVERSATION_RETENTION_DAYS` keep
working, but only as defaults. Nothing changes until someone stores a value, so an
installation that sets none of them behaves as before.

- Tenant admins can now switch the conversation log and the inbound media download per
  tenant on **Settings > Conversations**. A tenant that saves the form stores both
  switches as shown.
- Retention is the platform setting `conversation.retention_days`, in **Platform settings**
  (single mode) or with `php artisan platform:settings:set conversation.retention_days <days>`
  (host mode). `0` keeps the transcript forever. A `CONVERSATION_RETENTION_DAYS` above 3650
  keeps working as the default but cannot be stored.
- `CONVERSATION_STORE` stays an environment variable.

The upgrade adds two empty settings to every tenant, through the settings migrations
(see [Two schemas, two migration commands](#two-schemas-two-migration-commands)).

## New tenants go through a setup wizard

A tenant created after this release opens its console in a short first-run wizard
(content languages, first assistant) before anything else. Tenants that exist at
the upgrade are not affected: the settings migration marks them complete. To send
one back through the wizard, see
[the first-run setup wizard](/self-hosting/tenancy#the-first-run-setup-wizard).

The setup checklist on the dashboard is shown only to tenants that went through
the wizard (created after the release, or sent back through it); existing
tenants never see it. When a later upgrade or an activated Solution adds a
required setup step, a finished tenant is not held again: its staff see a banner
linking to the step, and its administrators get one bell notification.

## Message rate is per tenant

Sends are now throttled by each tenant's own rate, set on Tenant settings and stored
as 30 per minute when a tenant is provisioned. `MESSAGING_RATE_LIMIT_PER_MINUTE` is only
a fallback for sends outside a tenant, so an installation that set it to anything other
than 30 runs at 30 per tenant until an admin changes the tenant's rate. See
[Backpressure](/self-hosting/observability#backpressure).

## Operator-granted Solutions turn on by themselves

Only with an operator package installed: a Solution in the tenant's plan or in a running
add-on now runs automatically, and the tenant cannot turn it off — including a Solution
the tenant had turned off before the upgrade. Installations without an operator package
are not affected.

## Media storage can be S3

Nothing changes unless you set `MEDIA_STORAGE_DRIVER=s3`. An installation that already
has media must copy it to the bucket before switching; Core does not move stored files.
See [Media storage](/self-hosting/configuration#media-storage).

## Core images before 0.18.0 lack the console

The `core` images from 0.10.0 to 0.17.0 were built without the compiled console, so on an
installation from the Compose file every console page (`/admin/login` included) answers
500 while the `web` image looks healthy. Use 0.18.0 or later.

## Channel settings follow the channel type

A channel's settings form is now drawn from what its channel type declares, and saving a
channel keeps only the settings that type declares. A channel type that declares none —
the WhatsApp placeholder, or a connector's channel created before a connector declared
its settings — loses every stored setting the next time the channel is saved. Re-enter
them after the connector is updated.

The Telegram bot username moves into the channel's settings. A tenant migration moves
it, so `platform:update` is all it needs.

## Flow buttons

- A *text with keyboard* block that ends up with no buttons is sent as plain text, where
  it used to carry an empty inline keyboard.
- A fixed button whose label comes out empty (a missing translation, an empty variable)
  now sends the block through its error exit before anything is sent, instead of being
  refused by the provider.

## Horizon opens to staff on single installations

On a `single` installation, Horizon (`/horizon`) used to be closed to everyone. It now opens
for signed-in staff who hold the new **View operator screens** permission (`view_operator_screens`).
Administrators pass automatically, so after the upgrade every administrator can open the queue
dashboard, which shows job payloads. Custom roles do not hold the permission until you grant it; run
`php artisan ops:tenants-seed-acl` so the permission exists, then add it to the role. The tenant's
platform support user never opens it. `host` installations are unchanged: Horizon stays closed until
an operator package answers for it.

## PHP 8.5 and Laravel 13

Core now runs on Laravel 13 and requires PHP 8.5.12 or later. Releases of PHP before 8.5.12
are open to CVE-2026-109618 and CVE-2026-109619, two unauthenticated remote code execution
flaws fixed on 21 October 2026.

- **Docker Compose:** nothing to do beyond the usual upgrade. The images run PHP 8.5.
- **Bare metal:** install PHP 8.5.12 or later with the same extensions before upgrading
  (see [Requirements](/self-hosting/requirements)), point the web server and the
  PHP-FPM pool at it, and restart PHP-FPM, Horizon and the scheduler. On PHP 8.4,
  `composer install` refuses the release and the application refuses to boot.
  `deploy/install.sh` checks the patch release too.
- **Extension packages** must accept Laravel 13: an `illuminate/*` or `laravel/framework`
  constraint of `^12.0` stops Composer, so widen it, for example to `^12.0 || ^13.0`.
  `fapost/foundation` 0.29 and `fapost/support` 0.2.4 already do. Two framework changes
  can reach a package's code:
  - CSRF protection is now `Illuminate\Foundation\Http\Middleware\PreventRequestForgery`.
    `withoutMiddleware(ValidateCsrfToken::class)` no longer removes it, so routes that
    excluded it that way start answering 419; exclude `PreventRequestForgery` instead.
  - `Illuminate\Contracts\Mail\Mailer` gained `cc()`. A test double that implements the
    contract must add it.

## Extension packages and Foundation

Core now requires `fapost/foundation` ^0.29. A Solution, connector or operator package
installed next to it must accept that version, or Composer will not install the upgrade.

## Host-mode installs: sessions are now checked

An installation already running with `TENANCY_RESOLUTION=host` that has
`SESSION_DRIVER=database` or `SESSION_DOMAIN` set used to fail only on platform pages.
After this upgrade **every web request fails** with a message naming the setting.
Before upgrading, switch to `SESSION_DRIVER=redis` and unset `SESSION_DOMAIN`; people
sign in again once. Queue workers and console commands are not affected.

## Flow calls to internal addresses are refused

The `call` node no longer connects to private, loopback, link-local, reserved or
cloud-metadata addresses, and this applies to every installation. A flow that calls an
internal service (`http://crm.local`, `http://10.0.0.7/api`, a mock on `localhost`) now
takes its `error` handle with `error_code = egress_denied` instead of getting a
response. Redirects are checked on each hop, so a public URL that redirects to an
internal one is refused too.

Before upgrading, list the internal targets your flows rely on in `FLOW_EGRESS_ALLOW`
(for example `FLOW_EGRESS_ALLOW=10.20.0.0/16,crm.internal`), then restart Horizon. Cloud
metadata addresses cannot be listed.

Calls also stop honouring the `HTTP_PROXY` and `HTTPS_PROXY` environment variables. If
your calls leave the network through a proxy, set `FLOW_EGRESS_PROXY` to the same
address; that proxy must refuse private ranges itself. Names from `/etc/hosts` or
container aliases still resolve, but their addresses are checked like any other, so allow
them by range or name (a mock on `localhost` needs `FLOW_EGRESS_ALLOW=127.0.0.1/32`). See [Configuration](/self-hosting/configuration#outbound-calls-from-flows).

## Console route names and the assistant parameter

The console's routes lost the names they inherited from Filament, and the assistant in
an assistant's URL is now the route parameter `{assistant}` instead of `{tenant}`. The
addresses themselves did not change, so bookmarks and links keep working.

| Before | After |
|---|---|
| `filament.admin.resources.<resource>.<index\|create\|edit\|view>` | `console.admin.<resource>.<index\|create\|edit\|show>` |
| `filament.admin.pages.dashboard`, `.tenant-settings`, `.translations` | `console.admin.dashboard`, `console.admin.tenant-settings.edit`, `console.admin.translations.index` |
| `filament.assistant.resources.<resource>.<index\|create\|edit\|view>` | `console.<resource>.<index\|create\|edit\|show>` |
| `filament.assistant.pages.dashboard`, `.settings`, `.translations` | `console.dashboard`, `console.settings.edit`, `console.translations.index` |
| `filament.admin.auth.login`, `filament.assistant.auth.login` | `console.auth.login`, `console.auth.assistant-login` |
| `filament.assistant.tenant` (`/assistant`), `filament.assistant.home` (`/assistant/{id}`) | `console.entry`, `console.home` |

Only Solutions are affected. One that calls `route('filament.…')`, or passes
`['tenant' => …]` to a Console route or to its own `assistantRoutes()` route, must switch
to the new name and to `['assistant' => …]` before the upgrade; the old ones no longer
resolve. An action of an `assistantRoutes()` route receives its parameters by position,
so its signature does not change. Solutions that link to Core's screens through
`ConsoleTarget` keys, as [Console UI](/extending/console-ui) describes, need nothing.

## Downtime

The application tolerates a short window where old and new run side by side —
webhook ingress answers, and work queues up rather than being lost. What it does
not tolerate is old workers against a migrated schema, which is why they restart
last.

For a zero-downtime upgrade the ordering is: start new web containers, migrate,
then restart workers. Anything more elaborate is untested territory here.

## The gateway

The gateway upgrades independently of the application — it shares only Redis and
the queue format, both versioned.

```bash
docker compose --profile gateway pull
docker compose --profile gateway up -d
php artisan ops:ingress-specs-publish   # if adapters changed
php artisan gateway:doctor
```

If a release changes the queue payload version, the gateway and the application
must be upgraded together: the worker rejects a payload version it does not
recognise, sending the job to `failed_jobs` rather than processing it with half
its context. Release notes call this out when it applies.

## Rolling back

```dotenv
APP_VERSION=1.4.1
```

```bash
docker compose up -d
```

Code rolls back cleanly. **The database does not.** If the release you are leaving
contained migrations, restore the backup instead — or confirm from the release
notes that its migrations are additive, in which case older code simply ignores
the new columns.

## Verifying

```bash
docker compose ps                                     # all services up
docker compose exec app php artisan about              # version, environment, cache state
docker compose exec app php artisan horizon:status     # workers running the new code
docker compose logs --tail 50 horizon
```
