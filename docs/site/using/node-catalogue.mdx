Seventeen blocks, grouped the way the builder's palette groups them. Each does one
thing and reports an outcome; the flow decides what follows.

For the technical contract behind each — its type, version and configuration
schema — see [Flow node reference](/reference/flow-nodes).

## Core

The two blocks almost every flow uses.

### Send message

Sends a message to the contact on the channel they wrote from.

The **content type** decides what it sends: plain text, an image, a document, a
video, a voice message — or **text with a keyboard**, which turns this block into
something rather different from a send.

Message text is written per language on the builder's **Content** tab.

To message someone other than the contact of the conversation, fill in **Send to**:
a contact id, usually from a variable, such as `{{flow.customer_id}}`. A flow
started by a schedule, a webhook, an API call or a Core event has no contact, so there every
Send message block needs one. A message sent this way cannot wait for an answer: no
keyboard, timeout or saved answer. If the contact id comes out empty or malformed,
nothing is sent and the block leaves through its **error** exit with
`addressee_unresolved`. The text is in the flow's language, and `contact.*` in it
still means the contact of the conversation, which a flow without a contact cannot
read.

**Send to** can also name many people at once: **tags** (contacts with any of
them) or a **segment**. The block then starts a broadcast for the flow's assistant
and goes on at once, without waiting for it to finish; the broadcast appears on the
Broadcasts screen marked *From automation*, with the flow's name, and can be
cancelled there like any other. Such a message is text only — no media, keyboard or
saved answer — and must not use `contact.*` or `module.*`, since it goes to everyone
in the audience. Each language of the text is filled in when the block runs, and
each recipient gets it in their own language. Optionally give the broadcast a
**name** (otherwise the flow's name and the time) and a flow variable to **save**
`{broadcast_id, recipient_count}` to; the count is the reach when the block ran.

A step the engine repeats gets the same broadcast back, never a second one. While
the block's previous broadcast is still running, the block leaves through **error**
with `broadcast_running`; a segment that was deleted gives `audience_missing`, a text
with nothing in the base language `message_empty`. An audience nobody is in still
starts a broadcast, which completes with no recipients. Publishing a flow that adds
such a block, or changes its audience or text, needs the **Manage broadcasts**
permission. To act when the broadcast is done, start a flow on the
`core.broadcast.completed` event.

If the send fails, the flow leaves through the block's **error** exit, and the flow log
shows `send_failure: ...` with the reason on the block. When the
tenant has used up its outbound messages for the period, the message is not sent
and the flow leaves the same way, with the error type `limit_reached` (the flow
log shows it as `limit_reached: ...` on the block); a block
with nothing connected to its error exit ends the session.

#### The keyboard

Choosing *text with keyboard* reveals the keyboard section, and a **mode**:

| Mode | |
|---|---|
| **Inline** | Buttons attached to the message itself |
| **Reply** | Buttons replacing the contact's keyboard |

Buttons are built in two ways, and they can be combined.

**Fixed buttons** are listed by hand. Each has an **ID**, a **label**, and an
optional **value**.

<Warning>
  The label is translated; the **ID and value are not**. They are identifiers the
  flow compares against, so translating them silently breaks every condition that
  tests the answer — and it breaks it only for contacts in that language, which
  makes it hard to spot.
</Warning>

**Dynamic buttons** are generated from a value in the session. Point **source**
at a state path — `flow.items`, or something under `contact.` — and one button is
produced per entry, laid out **max per row** at a time (one to eight, two by
default).

Use dynamic buttons whenever the options are not known when the flow is written:
a list fetched by a [Call](#call), a set of appointment slots, whatever the
contact's own record holds.

Every fixed button needs a label once it is translated and its variables are filled
in. If one comes out empty, the message is not sent and the block leaves through its
error exit. A dynamic entry with an empty label is skipped instead.

#### Waiting for the press

A keyboard makes this block **wait**, the way [Input](#input) does. The flow does
not continue until the contact presses something or the block times out.

The **Response** section — collapsed by default — controls what happens then:

**Save answer to** stores the press at a state path. **Save answer variable**
does the same with more control: a name, a type (text, number, confirm), and
whether it is stored on the **session** or on the **contact**. Session storage
disappears when the session ends; contact storage stays.

**Timeout** is how long to wait before giving up and moving on.

#### Buttons that outlive the session

**Remove keyboard after press** is on by default: once the contact presses,
the keyboard goes.

Turn it off and something more interesting happens. Each button is registered
against the flow version and node that sent it, so a press is still understood
**after the session has ended** — the platform re-enters that branch and carries
on from there.

<Note>
  This is how a message stays useful long after the conversation ended: a
  confirmation sent last week can still be acted on today, and the flow resumes
  where the button pointed rather than starting over.

  It is also why leaving the keyboard in place is a decision rather than a
  cosmetic preference. Every such message is a live entry point into a flow, on a
  version of that flow which may since have been replaced.
</Note>

### Input

Asks the contact something and **waits for the answer**.

It validates what comes back and stores it, so the value is available to every
block after it. This is the only block that pauses a flow indefinitely: while it
waits, the session stays open, and if nobody answers it eventually times out
under the tenant's session lifetime.

If the question, or the hint shown after an invalid answer, cannot be sent because
the tenant has used up its outbound messages for the period, the session stops as
failed and is not retried; an answer given after the limit lifts does not resume the stopped session.

<Note>
  Input is where flows get stuck, and the *Current node* column in
  [Sessions](/using/sessions) is where that shows. Several contacts waiting on the
  same input usually means the question is unclear or the answer it accepts is
  narrower than what people naturally type.
</Note>

## Logic

Blocks that decide what happens next, or change the shape of the run.

### Branch

Splits the flow by condition. It covers both a simple yes/no test and a
multi-way switch, so one block handles "is this person a customer" and "which of
five options did they pick".

Each outcome is a separate connection. A branch that always reports the same
outcome is not branching — [Flow logs](/using/flow-logs) shows which one it
actually reported.

### Delay

Pauses before continuing.

Useful for pacing a conversation so a series of messages does not arrive as a
wall, and for waiting a defined period before a follow-up.

### Loop and Loop end

Repeats the blocks between them.

`Loop` opens the repetition and `Loop end` closes it; everything nested inside
runs each time round. The **Structure** panel in the builder is the practical way
to see what is inside a loop, since the main column can get long.

The loop keeps its count in a temporary variable, `iterator` by default (set the
name under advanced options), and, for a fixed number of repeats, the total in
`iterator_total`. Validate and publish refuse a flow where another block saves a
temporary variable with one of those names, and a fixed repeat count that is not a number. A **while** loop whose
condition no block inside the loop changes gets a warning: it may run until the
platform's iteration limit stops it. The warning does not block publishing, since
the value can change from outside the flow.

One loop repeats at most as many times as the installation's
[loop limit](/self-hosting/platform-settings) allows, 1000 by default: a fixed repeat
count above it is refused at publish, and a session that reaches it fails. A loop that
waits for the contact counts again from each message; in a conversation, a loop that keeps
working for more than 30 seconds without waiting — subflows it runs included — fails too. The steps inside a loop do not use
up the flow's general step limit, but one run never takes more than 10,000 steps, so a
loop with many blocks inside stops sooner.

To collect values across passes, turn on **Store as list** on the variable a block
saves. A list saved to the contact keeps its last 100 items by default; change
that under **Keep last** (1 to 1000). A list saved as a temporary variable is not
capped. Read the size of a list, or the length of a text, in any message or
condition as `{{contact.photos.length}}`; it is `0` when there is nothing yet.

### Subflow

Runs another flow, and **pauses this one until it finishes**.

This is how a piece of conversation gets reused — an address collection, an
identity check — without copying it into every flow that needs it. The parent
continues on `success`, `cancelled` or `failed`, after how the child ended.

The child has its own session variables (`flow.*`); contact data is shared. Two
optional lists move values between them:

- **Pass to the child flow** sets a child variable when the child starts. The value
  is text or an expression over this flow, such as `{{flow.user_id}}`; a value that
  is only one expression keeps its type, so a list stays a list.
- **Take back from the child flow** copies a child variable into a variable of this
  flow when the child ends with `success`, before the flow continues. A child
  variable that was never set arrives empty. Nothing is copied on `cancelled` or
  `failed`.

Names are variable names without the `flow.` prefix. Publishing refuses a name that
is not a valid variable name.

By default the subflow runs the flow's active version, so republishing the child
changes what every parent runs. To keep a parent on a tested version, enter its
number in **Pinned version**: that version keeps running after the child is
republished. Publishing refuses a version the child never published.

### Start flow for contact

Starts another flow as a **new conversation of a contact**, and goes on at once — it
does not wait for that conversation, as a [Subflow](#subflow) does.

Use it when something outside a conversation should reach a person: a scheduled
reminder, an order a [webhook](/using/webhook-trigger) reports, an event. Pick the
flow to start (a flow of the same assistant) and name the contact in **Contact**
with an expression, such as `{{flow.customer_id}}`. The contact is required: the
block never falls back to the contact of the run, so a flow without a contact can
use it too. The started conversation is the contact's with the bot of the flow you
picked, on the channel the contact used last.

**Pass to the started flow** sets temporary variables of the new conversation, as
the subflow's list does; a value that is only one expression keeps its type.

The block continues on one of four exits:

- `started` — the conversation is queued and starts within seconds. One step of
  the flow starts one conversation, even when the step is repeated after a
  failure; a loop over several contacts starts one per contact.
- `busy` — the contact is in the middle of something with that bot: an operator
  has the thread or one was requested, or a conversation with the bot moved in the
  last **Busy window** minutes (30 by default), or a conversation with the bot is
  waiting in a [Delay](#delay) to go on by itself. Nothing is sent. A live
  conversation older than the window is ended and replaced by the new one; with a
  window of 0 the contact is busy only while an operator has the thread. A
  conversation never starts a flow over itself: a flow that names its own contact
  on the same bot leaves by `busy`.
- `no_channel` — the contact has no channel on an active channel of that bot, so
  nothing could be delivered.
- `error` — the expression gave no contact id (`addressee_unresolved`), no
  contact has that id (`contact_not_found`), the flow has no active version
  (`target_inactive`), or flows starting each other went five levels deep
  (`chain_depth_exceeded`).

The block checks the contact again when the conversation actually starts; if the
contact became busy or lost the channel in between, nothing is started and this
flow does not learn of it. A private flow starts even for a contact who has not
passed authentication ([Visibility](/using/flows)): you wired the start yourself. To reach many contacts at once, use a
[broadcast](/using/broadcasts).

### Template

Places a [flow template](/using/flow-templates) in the flow as a single block.

Pick a published template of the same assistant. The block has one connection per
output the template defines, so the flow continues from whichever exit the template
reports. An output with nothing connected ends the session there. The template's
inner blocks are not shown in the flow; **Open template** opens it for editing.

If the template has [parameters](/using/flow-templates#parameters), the block's settings
show them; a value set there replaces the template's value in this flow, an empty one
keeps it.

The template runs in the same session as the flow and shares its variables.

### Template output

A named exit of a [flow template](/using/flow-templates). It exists only inside a
template and is not offered in ordinary flows.

Give it a name — lowercase latin letters, digits and `_`, starting with a letter —
and a label. The name becomes a connection on the **Template** block wherever the
template is placed; several outputs with the same name are one exit. It ends a branch
of the template, so it has no connections of its own.

### Emit event

Raises an event that can start other flows.

It does not wait: the event goes out and this flow carries on. Use it to set
something else in motion — a notification pipeline, a follow-up sequence —
without coupling the two flows together.

### Respond to webhook

Answers the system whose request started the flow, while it waits.

Only a [webhook trigger](/using/webhook-trigger#response-mode) or an [API trigger](/using/api-trigger#response-mode)
set to **Wait for the flow's answer** makes the caller wait. The block sets the status (200–499) and a JSON or text body built from the run's variables; the
first answer of a run is the one sent, and the flow carries on after it. Anywhere else — no such trigger, or the
caller already gave up — it does nothing.

### End

Finishes the flow explicitly.

A flow also ends by running out of blocks. `End` is for finishing early — after a
branch that concludes the conversation, for instance.

## Data

Blocks that record something rather than say something.

### Assign

Writes a value into the session.

It both stores plain values and transforms existing ones, so it covers "remember
what they answered" and "reformat it before using it". Values written here are
available to every block after it, and to conditions in branches.

### Set tag

Attaches a tag to the contact.

Tags outlive the session: they stay on the contact afterwards and can target a
[broadcast](/using/broadcasts) or feed a [segment](/using/segments). This is the
block that turns a conversation into something you can act on later.

## Integration

### Call

Calls another system — an HTTP endpoint, or an internal action.

It reports whether the call succeeded, so the flow can respond to a failure
rather than pretending it did not happen. Failed calls are retried before the
failure outcome is taken; how many times is a tenant setting.

By default an HTTP response counts as a success when its status is 2xx. **Success
statuses** (for example `200, 409, 3xx, 400-404`) replaces that rule: a listed status takes
the success outcome and an unlisted one the failure outcome. The **Test call** applies the
same rule.

Field mapping writes `null` for a path the response does not contain. With **Strict**
switched on, a successful call whose response lacks a mapped path takes the failure outcome
instead, with `error_code = mapping_missing` (the flow log shows `mapping_missing: <paths>`),
and none of the mapped variables is written.

**Authorization** can be a [saved credential](/using/credentials), picked by name for an HTTP
call; the secret is applied when the call runs and is not stored in the flow. The inline
**Bearer** and **Basic** modes put the secret in the flow definition itself, which is why the
builder marks them as stored there. A saved credential is sent only to its allowed hosts:
a call to another host is not made and takes the failure outcome with
`error_code = credential_host_denied`. Redirects are not followed when a credential is used.
The credential's headers or query parameter replace any of the same name the author set, and the
author's `Host` and forwarding headers are dropped. The secret is shown as `***` in the result,
the saved variables and the flow log. The other failures are `credential_not_found` (the
credential was deleted), `credential_unsupported` (the block does not use the HTTP transport) and
`credential_unavailable` (the secret cannot be read, for example after the application key changed).
Publishing is refused while the block names a missing credential or does not use the HTTP transport.

Each run of the block counts against the tenant's call executions for the
period, and so does every **Test call** in the builder. When they are used up the
call is not made and the flow takes the failure outcome, with
`error_code = limit_reached` (the flow log shows `limit_reached: ...` on the block).

An internal action that comes from a Solution works only while your workspace has that
Solution switched on. When it is off, the call is not made and the flow takes the failure
outcome, with `error_code = solution_inactive` (the flow log shows
`solution_inactive: ...` on the block); the Test call in the builder answers the same way. The
A Solution that is on but still preparing its tables for your workspace answers with `error_code = solution_not_ready` instead. The
action list in the builder shows only the actions you can use now.

<Warning>
  A call reaches outside the platform, so it is the block most likely to be slow
  or to fail. Give its failure outcome somewhere to go — a flow that only handles
  success leaves the contact with silence when the other system is down.
</Warning>

## AI

### Rag query

Asks the knowledge base a question and returns what it finds.

This is the block behind "answer from our documents": the contact's question goes
in, retrieved content comes back, and the flow decides what to do with it —
including what to do when nothing relevant was found.

## Contact

### Auth request

Checks that the contact is who they claim to be before continuing. A passed check
marks the contact authenticated, which opens [private flows](/using/flows) to them and
can be read later by a Branch block. Use it to gate anything that should not be
available to a stranger who found the bot.

Pick a **method**:

- **Basic** compares an answer the flow already has (a variable) with an expected value.
- **Phone number** asks the contact to share their own number with a button. A contact
  card someone forwarded, or a typed number, is not accepted. Set an **expected phone
  number** (for example one your CRM returned to a Call block) to accept only that
  number; without it the block proves only that the contact owns a Telegram account with
  a phone number. Needs a channel that can ask for a contact.
- **Code by email** sends a one-time code to the address you set (usually a contact
  attribute) and waits for the contact to type it back. The email has a fixed text in the
  contact's language, signed with the assistant's name; you write only the chat message
  that asks for the code. Name the **new code** button to let the contact ask for another
  one after a pause.
- **Code by SMS** works the same way over SMS, once an SMS connector is installed;
  publishing is refused without one.

The block has two outcomes: **Authenticated** and **Failed**. A failed check says why in
the flow log: too many wrong answers (`attempts_exhausted`), an expired code
(`expired`), a code that could not be delivered (`delivery_failed`) or too many codes
(`rate_limited`). For a phone check that ran out of attempts, the last refusal is given
as the detail: a forwarded contact card (`foreign_contact`) or a different number
(`phone_mismatch`). The code itself never appears in the flow, its variables or the flow
log, and is not accepted again once used.

Limits protect the address you send to: a code is 4 to 8 digits (6 by default) and works
for up to 30 minutes (10 by default), the contact has up to 10 attempts (5 by default) and
up to 5 codes per check (3 by default), and one address or number gets at most 5 codes an
hour in your workspace. A code sent by email or SMS counts against the workspace's
verification codes for the period, where the operator sets such a limit. An address taken
from what the contact typed is allowed, but publishing warns about it: anyone could have
codes sent to any address.

Blocks added before this version keep their single outcome and the Basic method.

### Notify

Sends a notification, in one of two modes.

**Staff** alerts people on your side — the escalation path when a conversation
needs a human. **Contacts** sends to contacts by tag or to all of them, through
the assistant, on the broadcast queue.

The second mode is a broadcast raised from inside a flow rather than composed by
hand, which is why it shares the pacing described in
[Broadcasts](/using/broadcasts).

## Conversation

Blocks that hand the conversation itself to someone.

### Request operator

Asks for a human operator and waits until one has dealt with the contact.

The conversation moves from the assistant to **Waiting for an operator**, and the
assistant stays silent while it waits; the contact's messages go to the inbox only.
Operators are chosen as in [Notify](#notify) (the assistant's staff, a role, or
specific users), but only those who can view and reply to conversations and have
access to the assistant are told. If nobody is left, the administrators are. They
get a bell notification that opens the conversation, and an email if you switch it
on. You can write a text for them; left empty, it says the contact is waiting for an
operator.

The contact is told in the block's own settings, in the content language:

- **Request sent** — with a **Cancel request** button where the channel supports
  buttons. The button goes away once the request stops waiting.
- **Operator connected** — optional, sent when an operator accepts.
- **Operator left** — sent when the operator finishes and returns the conversation
  to the assistant.

The block has three exits, and no `default`. An exit you leave unwired ends the
session.

| Exit | When |
|---|---|
| `returned` | The operator finished. "Operator left" goes out first, then the flow continues, for instance by asking for a rating. |
| `cancelled` | The contact pressed **Cancel request**. |
| `timeout` | Nobody accepted within **Wait for an operator** (300 seconds by default; `0` waits without a limit, and then `timeout` fires only when the request cannot be placed). |

When an operator accepts, the notifications dim for everyone and show who accepted;
a cancelled or expired request dims them too.

<Note>
  The conversation log must be enabled in the tenant settings. With it off, no
  request is placed: the block takes `timeout` at once, because an operator would
  see an empty thread. The same happens when the contact has no active channel. The
  wait itself needs an asynchronous queue; on a `sync` queue the timeout never
  fires, as with a [Send message](#send-message) timeout.
</Note>

If the conversation is already waiting for an operator, or an operator already
handles it, when the block runs, nobody is notified again and no "request sent" text
goes out. The session waits for that state, and finishing exits through `returned`.

`/reset`, `/cancel` and tenant commands that start a flow cancel the pending request
of the session they end: the conversation goes back to the assistant and the button
is removed. Informational commands do not. While an operator handles the
conversation, commands do not affect it.

The block is self-contained. To reuse a configured request, put it in a
[Subflow](#subflow) and map its exits with `End` blocks: `returned` to `success`,
`cancelled` to `cancelled`, `timeout` to `failed`. The parent cannot tell that
`failed` from the subflow's own error or timeout. Give that subflow a timeout longer
than an operator conversation (hours, for example `P1D`); otherwise it is ended
while the operator may still be talking, and the parent continues through `failed`.
Messages the flow sends are not blocked while an operator holds the conversation.

### Ask a person

Sends a question with buttons to a contact and waits for the answer.

The **addressee** is required: an expression that gives a contact id, such as
`{{flow.manager_id}}`. The question goes to that contact on the run's assistant, so
the block works in flows started by a schedule, a webhook, an event or the API, which
have no contact of their own, as well as in conversations. The block sets:

- **Question text** and **1 to 8 buttons**. A label is translatable; a button's value
  is the same in every language.
- **Wait** from 60 seconds to 7 days. Required.
- **Late answer text**, optional. See below.
- **Save the answer to**, optional: a variable that receives the pressed button's value.

The block has one exit per button, plus `timeout` and `error`. `error` is taken when
the addressee gives no contact id, when the run has no assistant or channel to send
through, when the message could not be sent, or when the question was lost.

The block's output in the run trace holds `answer`, `button_id`, `answered_by` and
`answered_at`, or `timed_out_at` when nobody answered, plus `question_id`. When the
wait was shortened (see below), `clamped_by_run_deadline` is set.

Only the addressee, on that assistant, can answer, and only with one of the
question's buttons. Anything else is ignored silently. A press never reaches the
addressee's own conversation and never starts a flow for them, even if the question
is unknown or gone, and it works while an operator holds the addressee's thread. An
accepted press removes the buttons and sends no text. A press after the decision,
after the timeout, or after the run ended or was reset gets the late answer text, or
the system text "This has already been decided." (an operator can override it per
tenant, like other system texts).

<Note>
  An automation run lives at most `flow.automation.max_run_hours` (24 hours by
  default), and the wait ends one minute before the run's deadline at the latest. With
  less than a minute left, the block takes `timeout` at once and asks nothing. To wait
  longer than a day, raise that platform setting.
</Note>

In a conversation, while the run waits, its own contact gets the usual "busy" reply,
and `/reset` ends the run. A question is deleted together with its run (under the
automation run retention) and with its addressee's contact.

## Annotation

### Comment

Not a step. A note for whoever reads the flow next.

It does nothing at runtime and costs nothing to add. A flow is read far more
often than it is written, and a condition that made obvious sense the day it was
written rarely does six months later.
