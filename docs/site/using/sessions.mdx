A session is one contact making one pass through one flow. This screen shows
them: what is running now, and what finished.

## The list

| Column | |
|---|---|
| **Session** | Its identifier |
| **Status** | Whether it is still running |
| **Outcome** | How it finished, once it has |
| **Contact** | Who is in it |
| **Flow** | Which flow they are in |
| **Current node** | Where they are right now |
| **Updated** | When it last moved |

By default the list shows only **live** sessions — running, waiting for the
contact's answer, or waiting for a subflow. The status filter switches to all
sessions or to one status; a session sleeping in a delay node is found under its
own status, *Paused*. Other filters narrow the list to one flow or to sessions
started within the last hour, day, week or 30 days, and the search finds a
session by the contact's channel user ID or contact ID.

The list keeps itself current: it updates as sessions move when your
installation has live updates switched on, and refreshes every 30 seconds
otherwise. A live session's page does the same; a finished one no longer changes.

## Current node is the useful column

It answers the question people actually arrive with: *where do conversations get
stuck?*

A handful of sessions sitting on the same node, all updated hours ago, is a
diagnosis. That node asked something people are not answering — the question is
unclear, the expected reply is not obvious, or the buttons offered do not cover
what they want to say.

<Note>
  Sessions waiting on a node that asks a question are normal. Sessions waiting on
  a node that should not wait at all — a message, a branch, a call — are not, and
  usually mean the step before it never completed.
</Note>

## Run graph

**Run graph** on a session's page draws the flow version the session ran as a
graph: the path it took is lit, nodes it never reached are dimmed, and each
card shows what happened there — done, waiting, failed or still running.

- **Branches** — what a condition's rule or a message's button leads to sits in a
  frame of that branch.
- **Subflows** — the run a subflow node started is drawn in a frame of its own
  next to that node; when the node started several, the latest is shown.
- **Loops** — a short, simple loop is unrolled: each pass is drawn in a frame of
  its own, with what every step did in that pass. Any other loop — one that ran
  more than five passes, has a long body, branches, calls a subflow or sits
  inside or around another loop — is drawn once, marked with how many passes it
  ran. Pick a pass above the graph to colour the path by that pass; by default
  the last one is shown.

Click a card to see the node's latest visits: when it ran, which exit it took,
how long it took and, for a failure, the error's type. A live session's graph
keeps itself current the same way the list does.

With the **View run payloads** permission, a visit that recorded data has a
**Show data** button: it loads that visit's input, output and error text, as the
run recorded them. Values under sensitive keys (tokens, passwords, keys) are
masked, and a large value is cut down to a `[truncated, N bytes]` marker. What
gets recorded:

- **Automation runs** record a node's input and output while recording is on in
  the platform settings; a visit from a time it was off shows no data.
- **Conversations** never record input and output — only the error text of a
  step that failed.

Without that permission the graph shows statuses only, and the node panel says
which permission shows the rest.

## Running a failed run again

A run an automatic trigger started — a webhook, an event — that **failed** can be
started again from the start: **Run again** on its page starts a new run with the
same data its trigger handed over, the request body or the event exactly as they
arrived, even if the flow changed them while it ran. The failed run stays as it
was; its page lists the runs started again from it, and each of those links back.

<Warning>
  Running again repeats everything the flow does. Every request to outside
  systems and every message the flow sends goes out again, and the systems on the
  other end see a new request, not a repeat. Make sure that is what you want
  before you confirm.
</Warning>

- The new run takes the flow's **current published version**. The confirmation
  says which, and says so when it is not the version the failed run ran — the
  usual case after fixing the flow.
- It is not offered for a conversation or for a subflow inside another run (run
  the outer run again), and only a run whose status is *Failed* can be run again —
  a run that reached an end node is not, whatever its outcome. It is refused when the
  trigger that started the run is turned off, deleted or
  [paused for starting too many runs](/using/publishing#when-a-trigger-starts-too-many-runs),
  the flow is switched off in the flows list, or the flow has no active version.
- Runs that failed before this was added kept no trigger data and cannot be run
  again.
- A double click, a second tab or a repeated request starts one run. To run it
  once more, wait until the page lists the new run and use the button again.
- It needs **View flow sessions & logs** and **Re-run failed automation runs** (see
  [Roles and permissions](/using/roles-and-permissions)), and each request is
  recorded in the [Activity log](/using/activity-log): a double click that
  starts one run can leave two entries for it.

## Status and outcome

**Status** is about now: is this session still live.

**Outcome** is about how it finished. A session can end because
the flow reached its end, because it was abandoned after waiting past the session
lifetime, or because execution failed.

The tenant-wide session lifetime decides how long a paused session survives — see
[Settings](/using/tenant-settings). Sessions abandoned by that timeout are the
usual reason a *Waiting sessions* count on the dashboard falls without anyone
doing anything.

## Session, conversation, or log

Three screens describe the same events from different angles, and picking the
right one saves time:

| Question | Screen |
|---|---|
| Where is this person stuck right now? | **Sessions** |
| What did they actually say? | [Conversations](/using/conversations) |
| What did the flow do, step by step? | [Flow logs](/using/flow-logs), or the session's **Run graph** |

A session points at a node. A log explains what that node did. A conversation
shows whether the person got what they came for.
