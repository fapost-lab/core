Commands FaPost Core registers, beyond Laravel's own.

## Installation

| Command | Does |
|---|---|
| `install` | Configure and install FaPost Core step by step |
| `platform:install` | Install the FaPost Core platform |
| `gateway:install` | Configure the webhook ingress gateway and generate its deployment files |

## Migrations and tenants

| Command | Does |
|---|---|
| `migrate:smart` | Show pending landlord and default local tenant migrations **without running them** |
| `ops:tenants-migrate` | Run `database/migrations/tenant` for all active tenants |
| `ops:tenants-seed-acl` | Run `TenantAclSeeder` — domain permissions and default roles — for selected active tenants |

## Platform update

| Command | Does |
|---|---|
| `platform:update` | The one upgrade command: validate the installed Solutions' manifests, run the landlord migrations and `ops:tenants-migrate`, then cache the Solution catalog |
| `platform:update --validate-only` | Only validate the manifests. Needs no database and changes nothing; exit code 1 and one `<package>: <field>: <message>` line per problem when a manifest is wrong |
| `solutions:cache` | Compile the Solution catalog into `bootstrap/cache/fapost-solutions.php` (part of `optimize`) |
| `solutions:clear` | Remove that file (part of `optimize:clear`) |

### Solutions

Activation is per tenant, so each command takes a required `--tenant=<slug>` and refuses to run without
it. There is no "every tenant" form. A Solution is off until activated.

| Command | Does |
|---|---|
| `solutions:activate {solution} --tenant=<slug>` | Turn an installed Solution on for the tenant. Refused (exit code 1) when the id is not installed with a valid manifest. Repeating it changes nothing |
| `solutions:deactivate {solution} --tenant=<slug> [--reason=]` | Turn it off for the tenant. Its data is kept. Allowed for a Solution that is no longer installed, to put out a stale record. The optional reason is kept in the activation journal |
| `solutions:list --tenant=<slug>` | List the Solutions installed in this image and the tenant's stored activation, orphans included, with the effective state. Changes nothing |

<Note>
  The cache is an accelerator only: when it is missing or older than the installed packages, the
  catalog is built from the package files. See [Upgrading and rollback](/self-hosting/upgrading).
</Note>

<Note>
  `migrate:smart` reports; it does not migrate. It exists so you can see what a
  release would apply before applying it. See
  [Upgrading and rollback](/self-hosting/upgrading).
</Note>

## Webhook routing

| Command | Does |
|---|---|
| `ops:webhook-warmup` | Write-through warmup: push all active channels to the Redis webhook registry per tenant |
| `ops:webhook-registry-health` | Check, and optionally repair, Redis-to-database consistency of the webhook routing registry |
| `ops:ingress-specs-publish` | Publish declarative channel ingress specs to Redis for the external gateway |
| `ops:ingress-migrate` | Report or migrate channels whose webhook still points at a previous ingress host |
| `gateway:doctor` | Verify that the gateway and the application share the same Redis, specs, and routing |

Webhook routing resolves through Redis rather than the landlord database, so the
registry is a cache with a source of truth behind it. `ops:webhook-registry-health`
is what tells you the two have diverged; `ops:webhook-warmup` is what rebuilds the
cache after a flush.

`gateway:doctor` is the first thing to run when the Go gateway is installed and
webhooks are not arriving — see [Webhook gateway](/self-hosting/gateway).

## Flow maintenance

| Command | Does |
|---|---|
| `flow:sweep-subflow-timeouts` | Force-fail subflow children whose parent has expired, and resume the parent through its failed handle |
| `flow:node-usage` | Report which node types and versions are still in use, per tenant and across the platform |
| `flow:audit-graph` | Report structural graph problems (no single entry node, unreachable nodes, duplicate handles, malformed variables) in active flow definitions and drafts, per tenant |

Run `flow:node-usage` before you remove a node handler or retire a handler version.
For each `type@version` it reports how many active flow definitions contain the node
and how often it executed recently, then names the nodes that have no registered
handler and the handler types no tenant uses at all.

The definition counts are the authoritative answer — a node in an active definition
runs sooner or later — while the execution counts reach back only as far as
`flow_logs` retention, which `logs:prune-flow` caps at 30 days. The command says so
on every run. Options: `--days` for the runtime window, `--tenant` for a single slug,
`--type` for a single node type, and `--json`.

`flow:audit-graph` changes nothing. Findings never change its exit code; it exits non-zero only when the audit itself could not run (an unknown `--tenant` slug, or a tenant that failed). Publishing does not check the
graph structure yet, so a flow can be active and still fail when a conversation starts.
Options: `--tenant` for a single slug and `--json`.

## Log partitions

| Command | Does |
|---|---|
| `logs:create-partition` | Create next month's `flow_logs` partition when missing |
| `logs:prune-flow` | Drop `flow_logs` monthly partitions older than 30 days |

`logs:prune-flow` accepts `--dry-run` to preview which partitions would be dropped.

## Conversation retention

| Command | Does |
|---|---|
| `conversations:prune` | Drop `conversation_messages` monthly partitions older than `CONVERSATION_RETENTION_DAYS`, in every active tenant. Does nothing when the variable is unset |

`conversations:prune` accepts `--dry-run`. Dropping is irreversible; threads and
media are kept. See [Conversation retention](/self-hosting/observability#conversation-retention).

## Limit refusals

| Command | Does |
|---|---|
| `limit-refusals:prune` | Delete records of work a per-period limit turned away that are older than `quota.refusals_retention_days` (90 days), in every active tenant. Scheduled daily at 04:00 |

<Warning>
  `logs:create-partition` is scheduled work. If the scheduler is not running,
  the partition for next month is never created — see
  [Services](/self-hosting/services).
</Warning>
