Nodes registered by Core. A handler is resolved by the pair `(type, version)`;
every Core node is at version 1, except `auth_request`, at version 2 (the ownership
checks and the `authenticated`/`failed` outputs); nodes published as `auth_request@1`
keep running on version 1.

| Category | Type | Label |
|---|---|---|
| Core | `input` | Input |
| Core | `send_message` | Send message |
| Logic | `branch` | Branch |
| Logic | `delay` | Delay |
| Logic | `loop` | Loop |
| Logic | `loop_end` | Loop end |
| Logic | `subflow` | Subflow |
| Logic | `emit_event` | Emit event |
| Logic | `end` | End |
| Logic | `webhook_response` | Respond to webhook |
| Data | `assign` | Assign |
| Data | `set_tag` | Set tag |
| Contact | `auth_request` | Auth request |
| Contact | `notify` | Notify |
| Conversation | `request_operator` | Request operator |
| Integration | `call` | Call |
| AI | `rag_query` | Rag query |

`type` is what a flow definition stores and what the registry resolves against. It
is unique across every registered handler, Core and extension alike, so an
extension picking a name that Core might later want is a collision waiting to
happen — prefix yours.

## Nodes the engine treats specially

Most nodes execute and return a handle. Four alter the shape of execution itself:

| Type | Effect |
|---|---|
| `end` | Sets the session status; the flow finishes |
| `loop_end` | Returns to the `loop` node named in its config |
| `subflow` | Creates a child session and pauses the parent until it completes |
| `input` | Returns `waiting`; the session pauses for the contact's reply |

## The `call` node and outbound addresses

A flow author controls the URL a `call` node requests, often through a template over
live state, so Core treats the target as untrusted. A request never reaches a private,
loopback, link-local, reserved or cloud-metadata address (for example `127.0.0.1`,
`10.0.0.0/8`, `169.254.169.254`, `::1`, `fd00::/8`). The check holds however the
address is reached: written directly, behind a DNS name, behind a name that answers
differently the second time, or at the end of a redirect.

- The host name is resolved by Core, every returned address must be public, and the
  connection is then made to exactly those addresses.
- Every redirect hop is checked again. Redirects stay on, up to 5, `http` and `https`
  only.
- Address forms that other software would read as an IPv4 address without being a
  canonical one (`2130706433`, `0x7f.1`, `127.1`, `0177.0.0.1`) are refused.
- Any port is allowed on a public address.

A refused call takes the `error` handle with `error_code = egress_denied`. The node
metadata and the builder test call carry the host and a reason (`private`, `loopback`,
`link_local`, `reserved`, `multicast`, `unspecified`, `metadata`, `invalid_host` or
`scheme_not_allowed`), never the resolved address. A name that does not resolve is
still `transport_failure`. A refused call still counts as one call execution.

An operator can allow trusted internal targets with `FLOW_EGRESS_ALLOW`; see
[Configuration](/self-hosting/configuration#outbound-calls-from-flows). Cloud
metadata addresses can never be allowed.

### The handler transport

The `handler` transport calls an in-process action by id (`target` is the id, for example
`feedback.submit`). Core builds the handler for each call in the job that makes it. An action
registered by a [Solution](/extending/solutions#registering-actions) runs only for a tenant that has
activated that Solution; otherwise the node takes the `error` handle with
`error_code = solution_inactive`, the flow log shows `solution_inactive: <solution id>`, and the
handler is not called. While the Solution's tenant tables are still being prepared, the same refusal is `solution_not_ready`. An id nobody registered is `action_not_found`; an exception in the handler is
`action_exception`. Every refusal counts as one call execution.

<Note>
  An extension that makes its own HTTP request from a flow parameter is not covered
  by this check. Such a request must refuse private, loopback, link-local and
  cloud-metadata addresses after the name is resolved and on every redirect hop. A
  shared contract for this will arrive with the first Solution that needs outbound
  HTTP; until then the extension carries the requirement itself.
</Note>

### Retrying a failed call

A `call` node can send a failed call again before it takes the `error` handle. The
optional `retry` object sets the sends in all (`max_attempts`, 1 to 5, default 3), the
first wait (`delay_ms`, 100 to 5000, default 500), the `backoff` (`exponential`, the
default, doubles it up to 5 seconds; `fixed` keeps it) and which failures are retried
(`on`: `network`, `5xx`, `429`, all three by default). A `Retry-After` header in seconds
is honoured when it asks for longer.

Every send carries the same `Idempotency-Key` and the next `X-FaPost-Attempt-Number`,
and the node spends one call execution however many sends it makes. A status the node
accepts as success (`success_statuses`) is never retried, and nor is another 4xx, a
refused address or an invalid target.

The waits happen inside the step, so the retries must fit in 18 seconds from the first
send, counting up to 8 seconds for the name lookup; a retry's timeout is cut to what is
left. With the default 10-second timeout a call that timed out is usually not retried
(the node metadata says `retry_stopped: window`): lower the timeout to retry slow calls.
The builder's test call sends once.

## Declaring a node

`type`, `version`, `label`, and `category` come from the handler. Core handlers
extend `AbstractVersionedHandler`, which derives them from a `TYPE` constant:

```php
final class SendMessageNodeHandler extends AbstractVersionedHandler
{
    final public const string TYPE = 'send_message';

    public function version(): int
    {
        return 1;
    }
}
```

The base class defaults `label()` to a humanised form of the type. Always override
`category()` and return a `NodeCategory` value (or, for a Solution, its id): the
base class still returns `Core`, which is not a palette group and fails the boot.
That default is deprecated and becomes abstract in Foundation 1.0.

See [Handler contract](/extending/flow-nodes/handler-contract) for the full
interface and [Versioning](/extending/flow-nodes/versioning) for when the version
must change.
