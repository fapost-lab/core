## Контекст

Staff Domain содержит users, roles, permissions. Необходимо зафиксировать набор системных ролей, матрицу прав, механизм иерархической защиты и возможность деактивации аккаунтов без удаления.

---

## 1. Системные роли

Три встроенные роли. Создаются только через `RoleSeeder`, не через UI. Удаление через UI заблокировано (`is_system = true`).

| Роль | Priority | Scope |
| --- | --- | --- |
| `admin` | 100 | Полный доступ: боты, flow, рассылки, RAG, пользователи, настройки тенанта |
| `content_manager` | 50 | Flow (create/edit), broadcast (manage), RAG (edit), контакты (список + теги/сегменты, без мета) |
| `analyst` | 30 | Аналитика и дашборды — только read-only. Нет доступа к flow, ботам, пользователям |

> ⚠ Кастомные роли (`is_system = false`) создаются через UI администратором. Priority кастомной роли — строго ниже priority создающего.
>

## 2. Матрица прав (permissions)

Права моделируются как укрупнённые блоки (`manage_*` / `view_*`). `Permission` — отдельный enum, активно используется в коде для генерации карт и проверок.

| Permission | Роли | Описание |
| --- | --- | --- |
| `manage_bots` | admin | Создание, редактирование, удаление ботов, webhook |
| `manage_users` | admin | Управление staff-аккаунтами, назначение ролей, деактивация |
| `manage_flow` | admin, content_manager | Создание, редактирование, активация/деактивация flow |
| `manage_broadcast` | admin, content_manager | Создание и запуск рассылок |
| `manage_rag` | admin, content_manager | Редактирование базы знаний, документы, конфиг провайдера |
| `view_contacts` | admin, content_manager | Просмотр списка контактов + теги/сегменты (без мета: телефон, username) |
| `manage_contacts` | admin | Редактирование тегов, сегментов, групп контактов |
| `view_analytics` | admin, content_manager, analyst | Дашборды, воронки, статистика flow и рассылок |
| `view_system` | admin | Horizon UI, логи, очереди в Filament — системный раздел |
| `manage_settings` | admin | Настройки тенанта: интеграции, уведомления, конфиг |

> ⚠ `content_manager` видит контакты (список + теги/сегменты), но не мета-данные: телефон, username, channel_id. Фильтрация на уровне scope в `ContactResource`.

## 3. RoleEnum + RoleSeeder

Единственный источник истины для системных ролей — `RoleEnum`. Seeder итерирует `cases()`, никакой дублирующей логики.

**Добавить новую системную роль** = добавить `case` в enum с `priority()` и `permissions()`. Seeder не трогаем.

```php
// app/Domains/Staff/Enums/RoleEnum.php

enum RoleEnum: string
{
    case Admin          = 'admin';
    case ContentManager = 'content_manager';
    case Analyst        = 'analyst';

    public function priority(): int
    {
        return match($this) {
            self::Admin          => 100,
            self::ContentManager => 50,
            self::Analyst        => 30,
        };
    }

    public function permissions(): array
    {
        return match($this) {
            self::Admin          => Permission::cases(),
            self::ContentManager => [
                Permission::ManageFlow,
                Permission::ManageBroadcast,
                Permission::ManageRag,
                Permission::ViewContacts,
                Permission::ViewAnalytics,
            ],
            self::Analyst => [
                Permission::ViewAnalytics,
            ],
        };
    }
}
```

```php
// database/seeders/RoleSeeder.php

public function run(): void
{
    foreach (CoreRegistrar::getRoles() as $role) {
        $model = Role::firstOrCreate(
            ['name' => $role->value()],
            ['priority' => $role->priority(), 'is_system' => $role->isSystem()],
        );

        $model->syncPermissions(
            array_map(fn($p) => $p->value, $role->permissions())
        );
    }
}
```

> ⚠ Seeder читает через `CoreRegistrar::getRoles()` — в Фазе 1 возвращает `RoleEnum::cases()`, в Фазе 4 собирает также роли из модулей. Логика seeder не меняется.
>

## 4. Изменения в миграциях

| Поле | Описание |
| --- | --- |
| `users.is_active` (bool, default true) | Флаг активности аккаунта. false — вход заблокирован немедленно |
| `roles.priority` (smallint, default 0) | Числовой приоритет. Нельзя назначить роль с priority ≥ своего |
| `roles.is_system` (bool, default false) | Системная роль — не удаляется через UI, только через seeder/код |

## 5. Деактивация пользователя (is_active)

### Поведение

- `is_active = false` → немедленная инвалидация сессии
- `UserService::deactivate()` вызывает `Auth::logoutOtherDevices()` + удаление всех `remember_tokens`
- `EnsureUserIsActive` middleware проверяет флаг на каждый запрос — заблокированный пользователь получает 401 даже с живым токеном
- Повторная активация: `is_active = true`, сессии не восстанавливаются — требуется новый логин

### Защитные инварианты

- Нельзя деактивировать единственного активного admin — guard в `UserService`
- Нельзя деактивировать себя через UI — скрыто в Filament action + проверка в Policy

> ✕ Деактивация — не удаление. Все данные пользователя сохраняются. Аккаунт можно повторно активировать.
>

## 6. Иерархия ролей и UserPolicy

### Два gate-метода

**`updateProfile(User $actor, User $target)`**

- Себе — разрешено всегда (кроме смены ролей)
- Чужим — только если priority актора строго выше priority цели

**`updateRoles(User $actor, User $target, array $roleIds = [])`**

- Себе — ВСЕГДА запрещено
- Чужим — только если `actorOutranks($target)`
- Назначаемые роли — только с priority строго ниже priority актора

### Инварианты

| Сценарий | Результат |
| --- | --- |
| Менеджер меняет себе роль | ❌ updateRoles → false (self) |
| Менеджер меняет роль пользователю с priority ≥ своего | ❌ actorOutranks → false |
| Менеджер назначает роль с priority ≥ своего | ❌ maxRolePriority ≥ actorPriority → false |
| Менеджер назначает analyst (30) другому пользователю | ✅ Разрешено |
| Деактивация пользователя: is_active = false | ✅ Сессия убивается немедленно, логин заблокирован |
| Деактивированный пользователь пытается войти | ❌ EnsureUserIsActive middleware → 401 |
| Деактивация единственного admin-аккаунта | ❌ Guard в UserService → исключение |

## 9. Архитектурная заметка: роли модулей (Фаза 4)

Текущая реализация покрывает только платформенные роли. При появлении модулей (Фаза 4) каждый модуль регистрирует свои роли через `CoreRegistrar`:

```php
// В ServiceProvider модуля:
CoreRegistrar::roles(HrRoleEnum::cases());
CoreRegistrar::permissions(HrPermission::cases());
```

`RoleEnum` и `HrRoleEnum` реализуют `RegisterableRoleInterface` — `RoleSeeder` работает с ними одинаково.

```php
interface RegisterableRoleInterface
{
    public function value(): string;
    public function priority(): int;
    public function isSystem(): bool;
    public function permissions(): array;
}
```
